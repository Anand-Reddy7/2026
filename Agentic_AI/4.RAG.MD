# What is RAG, and why does our Kubernetes agent need it?

**RAG = Retrieval-Augmented Generation.**

> RAG retrieves relevant information from an external knowledge source and provides it to the LLM as context before the LLM generates its answer.

In our project, the external knowledge is our **Kubernetes troubleshooting runbooks stored in Qdrant**.

## Without RAG

Suppose the agent finds:

```text
Pod: nginx-app
Status: ImagePullBackOff
```

The LLM has its pretrained Kubernetes knowledge, but it doesn't automatically know **our organization's troubleshooting procedures or runbooks**.

```text
User Question
     ↓
LLM
     ↓
Answer based mainly on pretrained knowledge
```

This can increase the chance of unsupported or inappropriate recommendations.

## With RAG

```text
User: "Why is nginx-app failing?"
        ↓
       LLM
        ↓
Live investigation through MCP
        ↓
ImagePullBackOff
        ↓
search_book("ImagePullBackOff troubleshooting")
        ↓
Qdrant
        ↓
Relevant runbook chunks
        ↓
LLM
        ↓
Grounded troubleshooting response
```

Qdrant could retrieve content from:

```text
knowledge/image_pull_runbook.md
```

The LLM then reasons using both:

```text
MCP → What is actually happening in the cluster
RAG → How our knowledge/runbooks say to troubleshoot it
```

## Why not put all runbooks in the prompt?

With hundreds or thousands of runbooks, sending everything causes:

```text
Huge context
Higher token cost
Higher latency
More irrelevant information
Context-window pressure
```

RAG retrieves only relevant pieces:

```text
10,000 documents
       ↓
Vector Search
       ↓
Top 3 relevant chunks
       ↓
LLM
```

Our implementation:

```python
retriever = vectorstore.as_retriever(
    search_kwargs={"k": 3}
)
```

## RAG has two main stages

### Offline / ingestion

```text
Kubernetes Runbooks
        ↓
Load documents
        ↓
Chunk documents
        ↓
OpenAI Embeddings
        ↓
Vectors
        ↓
Qdrant
```

Our embedding model:

```text
text-embedding-3-small
```

### Runtime / retrieval

```text
User/problem
     ↓
Query embedding
     ↓
Qdrant similarity search
     ↓
Top-K relevant chunks
     ↓
LLM context
     ↓
Answer
```

Remember:

```text
Ingestion:
Documents → Chunks → Embeddings → Qdrant

Retrieval:
Query → Embedding → Search Qdrant → Relevant Chunks → LLM
```

## RAG vs MCP in our agent

| MCP | RAG |
|---|---|
| Live operational data/actions | Knowledge retrieval |
| Current pod status | Troubleshooting runbook |
| Current events | Recommended investigation steps |
| Current logs | Internal documentation |
| Can perform controlled actions | Provides relevant context |

Example:

```text
MCP:
"nginx-app is ImagePullBackOff"

RAG:
"For ImagePullBackOff, inspect image name, tag, registry access and events."

LLM combines both.
```

RAG does **not** replace MCP, and MCP does **not** replace RAG.

## Does RAG eliminate hallucination?

No.

RAG **reduces hallucination by grounding the model in retrieved evidence**, but the LLM can still misunderstand retrieved information or receive irrelevant retrieval results.

We still need:

```text
Good retrieval
Relevant Top-K
Metadata filtering
Evaluation
Tool grounding
Validation
HITL for writes
```

## Interview Answer

> **RAG stands for Retrieval-Augmented Generation. It allows an LLM to retrieve relevant information from an external knowledge source and use that information as context when generating a response. In my Kubernetes agent, I use RAG for troubleshooting runbooks. The runbooks are chunked, converted into embeddings and stored in Qdrant. At runtime, the agent's RAG tool performs semantic retrieval and returns the most relevant runbook chunks to the LLM. MCP provides live Kubernetes state, while RAG provides troubleshooting knowledge. This grounds the LLM in both current cluster observations and relevant operational documentation instead of relying only on its pretrained knowledge.**

## Remember

```text
MCP → What's happening now?
RAG → What knowledge is relevant?
LLM → Reason over both
```

# What are Embeddings, and How Are They Generated?

An **embedding is a numerical representation of text that captures its semantic meaning**.

Simply:

> **Embedding converts text into a vector (array of numbers) so computers can compare the meaning of different pieces of text.**

## Kubernetes example

Suppose our runbook contains:

```text
Pod is failing because the container image cannot be pulled.
```

The embedding model converts it into something conceptually like:

```text
[0.12, -0.43, 0.81, 0.22, ...]
```

In our project we use:

```python
OpenAIEmbeddings(
    model="text-embedding-3-small"
)
```

Our current vectors have **1536 dimensions**.

```text
Text
 ↓
Embedding Model
 ↓
1536 numbers
 ↓
Vector
```

## Why do we need embeddings?

Computers cannot directly perform semantic similarity search over natural-language meaning.

Consider:

```text
Runbook:
"Container image cannot be downloaded"

User:
"Pod has ImagePullBackOff"
```

These sentences don't contain exactly the same words, but they are semantically related.

Their vectors should therefore be relatively close in the embedding space.

```text
"ImagePullBackOff"
        ↓
     Vector A
        ↘
       similar

"Container image cannot be downloaded"
        ↓
     Vector B
```

This enables **semantic search**.

## How embeddings work in our RAG

During ingestion:

```text
Runbook
   ↓
Chunking
   ↓
Chunk 1
Chunk 2
Chunk 3
   ↓
Embedding Model
   ↓
Vector 1
Vector 2
Vector 3
   ↓
Qdrant
```

For example:

```text
image_pull_runbook.md
        ↓
      chunks
        ↓
text-embedding-3-small
        ↓
1536-dimensional vectors
        ↓
Qdrant
```

Qdrant stores the vector together with the associated chunk/payload information.

## What happens when the user searches?

Suppose the agent searches:

```text
How do I troubleshoot ImagePullBackOff?
```

The **same embedding model** converts the query:

```text
Query
 ↓
text-embedding-3-small
 ↓
Query Vector
```

Qdrant then compares that query vector against stored vectors.

```text
                    Query Vector
                         ↓
                       Qdrant
                    /     |     \
                   /      |      \
             Vector 1  Vector 2  Vector 3
                 ↓        ↓         ↓
              score     score      score
```

The most similar vectors represent the most relevant chunks.

Those chunks are returned to the LLM.

```text
Query
 ↓
Embedding
 ↓
Vector Search
 ↓
Top-K chunks
 ↓
LLM
 ↓
Answer
```

## Embedding model vs LLM

Don't confuse them.

```text
Embedding Model
→ Text → Vector

LLM
→ Context → Generate/reason about text
```

In our application:

```text
text-embedding-3-small
        ↓
Used for retrieval

ChatOpenAI
        ↓
Used for reasoning/generation
```

The embedding model doesn't generate the troubleshooting answer.

It helps us **find relevant information**.

## Interview Answer

> **An embedding is a numerical vector representation of text that captures semantic meaning. In my Kubernetes RAG pipeline, I split troubleshooting runbooks into chunks and use an embedding model such as `text-embedding-3-small` to convert each chunk into a vector, which is stored in Qdrant. At query time, the user's search query is converted into a vector using the same embedding model, and Qdrant compares that query vector with stored vectors to retrieve semantically similar runbook chunks. Those chunks are then provided to the LLM as context for generating the response.**

## Remember

```text
Text
 ↓
Embedding Model
 ↓
Vector
 ↓
Qdrant

Query
 ↓
Embedding Model
 ↓
Query Vector
 ↓
Similarity Search
 ↓
Relevant Chunks
```

# What is a Vector Database, and Why Are We Using Qdrant?

A **vector database is a database designed to store, index, and search high-dimensional vectors efficiently**.

In our project:

```text
Kubernetes Runbook Chunk
        ↓
Embedding Model
        ↓
1536-dimensional vector
        ↓
Qdrant
```

Qdrant stores the vectors and lets us find vectors that are **semantically similar** to a query vector.

## Why can't we just use a normal database?

A normal relational database is excellent for exact/structured queries:

```sql
SELECT * FROM runbooks
WHERE error = 'ImagePullBackOff';
```

But the user might ask:

```text
Why can't Kubernetes download my container image?
```

while the document contains:

```text
Troubleshooting ImagePullBackOff
```

The wording is different, but the meaning is similar.

A vector database allows:

```text
"Why can't Kubernetes download my container image?"
                    ↓
              Query Embedding
                    ↓
                  Qdrant
                    ↓
            Similarity Search
                    ↓
        ImagePullBackOff Runbook
```

That's **semantic search** rather than exact keyword matching.

## What does Qdrant store?

Conceptually, each point can contain:

```text
Point
├── ID
├── Vector
│    └── [0.12, -0.43, 0.81, ...]
│
└── Payload / metadata
     ├── text
     ├── source
     └── other metadata
```

For our RAG pipeline:

```text
Runbook
 ↓
Chunks
 ↓
Embeddings
 ↓
Qdrant Points
```

We currently have vectors of size:

```text
1536
```

and use:

```text
Cosine
```

as the distance/similarity metric.

## Why Qdrant?

For our project, Qdrant gives us the capabilities we need:

```text
Vector storage
+
Similarity search
+
HNSW indexing
+
Top-K retrieval
+
Payload/metadata
+
Metadata filtering
```

It also integrates easily with LangChain:

```python
vectorstore = QdrantVectorStore.from_existing_collection(
    embedding=embeddings,
    collection_name="kubernetes_runbooks",
    url="http://localhost:6333"
)
```

Then:

```python
retriever = vectorstore.as_retriever(
    search_kwargs={"k": 3}
)
```

So our application doesn't have to implement vector search itself.

## Where Qdrant fits

```text
                 RAG
                  │
         ┌────────┴────────┐
         │                 │
     Ingestion          Retrieval
         │                 │
     Runbooks            Query
         ↓                 ↓
      Chunks           Embedding
         ↓                 ↓
    Embeddings           Qdrant
         ↓                 ↓
       Qdrant         Top-K Chunks
                           ↓
                          LLM
```

## Qdrant vs PostgreSQL in our application

Don't confuse them:

```text
Qdrant
   ↓
Semantic knowledge retrieval
Kubernetes runbooks
Embeddings
Vector search


PostgreSQL
   ↓
LangGraph workflow persistence
Conversation state
Checkpoints
HITL resume state
```

## Interview Answer

> **A vector database is designed to store and efficiently search high-dimensional vectors generated by embedding models. In my Kubernetes RAG system, runbook chunks are converted into 1536-dimensional embeddings and stored in Qdrant. At runtime, the query is also embedded, and Qdrant performs similarity search to retrieve the most semantically relevant runbook chunks. I use Qdrant because it provides vector indexing, similarity search, HNSW-based approximate nearest-neighbor search, payload metadata and filtering, and it integrates well with LangChain.**

## Remember

```text
Normal DB
→ structured/exact lookup

Vector DB
→ semantic similarity search

Qdrant
→ vector database used by our Kubernetes RAG
```

# How Does Semantic Search Work?

**Semantic search retrieves information based on meaning, not only exact keyword matches.**

In our Kubernetes RAG system, semantic search works by comparing the **embedding of the search query** with the **embeddings of our stored runbook chunks**.

## Kubernetes Example

Suppose our runbook contains:

```text
The container image cannot be downloaded from the registry.
```

But the query is:

```text
How do I troubleshoot ImagePullBackOff?
```

A keyword-only search may depend heavily on matching words.

Semantic search can recognize that these texts discuss related concepts because their embeddings should be relatively close.

```text
"How do I troubleshoot ImagePullBackOff?"
                    ↓
               Embedding
                    ↓
              Query Vector
                    ↓
                 Qdrant
                    ↓
       Compare with stored vectors
                    ↓
"The container image cannot be downloaded..."
```

## Step 1: Runbooks are embedded during ingestion

We already perform:

```text
Runbook
   ↓
Chunking
   ↓
Chunk
   ↓
Embedding Model
   ↓
Vector
   ↓
Qdrant
```

Example conceptually:

```text
Chunk A: ImagePullBackOff troubleshooting
Vector A: [0.12, -0.43, ...]

Chunk B: OOMKilled troubleshooting
Vector B: [0.73, 0.11, ...]

Chunk C: DNS troubleshooting
Vector C: [-0.32, 0.54, ...]
```

## Step 2: The query is embedded

At runtime:

```text
"Why can't Kubernetes pull my image?"
               ↓
       Embedding Model
               ↓
         Query Vector
```

The query and documents must be represented in a compatible embedding space.

## Step 3: Qdrant searches for nearby vectors

Qdrant compares the query vector with stored vectors using our configured metric:

```text
Cosine
```

Conceptually:

```text
                    Query Vector
                         │
              ┌──────────┼──────────┐
              ↓          ↓          ↓
          ImagePull     OOM       DNS
           Vector      Vector     Vector

          closest
             ↓
      most relevant
```

## Step 4: Top-K results are returned

Our retriever currently uses:

```python
retriever = vectorstore.as_retriever(
    search_kwargs={"k": 3}
)
```

Therefore:

```text
Query
 ↓
Qdrant search
 ↓
Rank results by similarity
 ↓
Top 3 chunks
```

Those chunks are returned to the agent.

## Step 5: LLM uses retrieved context

The final flow is:

```text
User Query
    ↓
Query Embedding
    ↓
Qdrant
    ↓
Similarity Search
    ↓
Top-K Runbook Chunks
    ↓
LLM
    ↓
Grounded Answer
```

## Keyword Search vs Semantic Search

```text
Keyword search
→ looks primarily for matching terms

Semantic search
→ searches using vector representations of meaning
```

Example:

```text
Query:
"Pod cannot download container image"

Document:
"Troubleshooting ImagePullBackOff"
```

Even though the wording differs, semantic retrieval can identify the relationship.

## Important Point

Semantic similarity does **not automatically mean the result is correct or sufficiently relevant**.

The nearest vectors are simply the best matches found under the configured retrieval method.

That's why production RAG systems also consider:

```text
Top-K
Similarity scores
Relevance thresholds
Metadata filtering
Reranking
Hybrid search
RAG evaluation
```

## Interview Answer

> **Semantic search retrieves information based on semantic meaning rather than only exact keyword matches. In my Kubernetes RAG system, runbook chunks are converted into embeddings and stored in Qdrant. At runtime, the troubleshooting query is converted into an embedding using the same embedding model. Qdrant compares the query vector with stored vectors using cosine similarity and retrieves the Top-K nearest runbook chunks. These chunks are then provided to the LLM as grounding context. This allows a query such as 'container image cannot be downloaded' to retrieve an ImagePullBackOff runbook even when the wording is different.**

## Remember

```text
Query
 ↓
Embedding
 ↓
Query Vector
 ↓
Qdrant
 ↓
Vector Similarity
 ↓
Top-K Chunks
 ↓
LLM
```

# What is Cosine Similarity?

**Cosine similarity measures how similar two vectors are by comparing the angle between them.**

In our Kubernetes RAG system, it helps determine how closely the **query embedding** matches the **runbook chunk embeddings** stored in Qdrant.

## Simple idea

Imagine two vectors:

```text
A ↗
B ↗
```

If they point in almost the same direction, they are highly similar.

If they point in very different directions, they are less similar.

```text
Small angle  → Higher cosine similarity
Large angle  → Lower cosine similarity
```

## Formula

```text
cosine_similarity(A, B) = (A · B) / (||A|| × ||B||)
```

Where:

```text
A · B   = dot product
||A||   = magnitude of vector A
||B||   = magnitude of vector B
```

The important interview concept is that cosine similarity primarily compares **direction**, rather than simply comparing vector magnitude.

## Kubernetes RAG example

Stored runbook:

```text
Troubleshooting ImagePullBackOff caused by an invalid container image.
```

Query:

```text
Why can't my pod download its container image?
```

Both are converted into embeddings:

```text
Runbook text
    ↓
Runbook Vector

Query
    ↓
Query Vector
```

Qdrant compares them:

```text
Query Vector
     ↓
Cosine comparison
     ↓
Stored Runbook Vectors
     ↓
Ranked matches
```

The ImagePullBackOff runbook should ideally rank higher than unrelated runbooks such as DNS or OOMKilled.

## Conceptual example

Suppose retrieval produces:

```text
ImagePullBackOff chunk → 0.91
Registry issue chunk   → 0.86
OOMKilled chunk        → 0.32
DNS chunk              → 0.20
```

Higher similarity indicates a closer semantic match.

These numbers are only illustrative; actual score semantics depend on the vector database and retrieval API.

## Why cosine instead of comparing raw numbers?

Embedding vectors may contain hundreds or thousands of dimensions.

Our current embeddings have:

```text
1536 dimensions
```

Manually comparing those numbers is not useful.

Cosine similarity reduces the comparison to a similarity measure that can be used to rank vectors.

## Where it fits in our flow

```text
User Query
    ↓
Embedding Model
    ↓
Query Vector
    ↓
Qdrant
    ↓
Cosine-based Vector Comparison
    ↓
Nearest Vectors
    ↓
Top-K Runbook Chunks
    ↓
LLM
```

Our Qdrant collection is configured with:

```text
distance = Cosine
```

## Cosine similarity is not the same as Top-K

These are different concepts.

```text
Cosine similarity
→ measures/ranks how similar vectors are

Top-K
→ controls how many highest-ranked results we retrieve
```

For example:

```text
Qdrant ranks:
1. ImagePullBackOff
2. Registry authentication
3. Image tag issue
4. DNS
5. OOMKilled

k = 3
```

We return only:

```text
1. ImagePullBackOff
2. Registry authentication
3. Image tag issue
```

## Important production point

The best available match is not necessarily a good match.

For example, if all stored documents are unrelated, Qdrant can still return the nearest vectors.

That leads to the next important concepts:

```text
Similarity score
Relevance threshold
```

These help us decide whether retrieved chunks are relevant enough to use.

## Interview Answer

> **Cosine similarity measures the similarity between two vectors based on the angle between them. In my Kubernetes RAG system, the user's troubleshooting query and the runbook chunks are converted into embeddings. Qdrant uses cosine-based vector comparison to find the stored vectors closest to the query vector and ranks the corresponding runbook chunks. We then retrieve the Top-K results and provide them to the LLM as grounding context.**

## Remember

```text
Embedding → Vector

Query → Query Vector

Query Vector
      ↓
Cosine Comparison
      ↓
Closest Runbook Vectors
      ↓
Top-K
      ↓
LLM
```

# What is Chunking, and Why Do We Chunk Documents Before Embedding?

**Chunking means splitting a large document into smaller pieces before creating embeddings.**

In our Kubernetes RAG system:

```text
Kubernetes Runbook
       ↓
    Chunking
       ↓
Chunk 1
Chunk 2
Chunk 3
       ↓
Embeddings
       ↓
Qdrant
```

## Why not embed the complete runbook?

Suppose `kubernetes_runbook.md` contains:

```text
Pod troubleshooting
Deployment troubleshooting
Service troubleshooting
DNS troubleshooting
Storage troubleshooting
Resource troubleshooting
```

If we create one embedding for the entire document, that single vector has to represent many different topics.

A query such as:

```text
Why is my pod stuck in Pending?
```

would be compared with the vector representing the entire document.

Instead, if we split the document:

```text
Chunk 1 → Pod Pending troubleshooting
Chunk 2 → Deployment troubleshooting
Chunk 3 → Service troubleshooting
Chunk 4 → DNS troubleshooting
```

the query can match directly with the most relevant section.

```text
"Why is my pod Pending?"
          ↓
      Embedding
          ↓
       Qdrant
          ↓
Chunk 1: Pod Pending troubleshooting
```

This improves retrieval precision.

## Our current implementation

We use:

```python
RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=100
)
```

Conceptually:

```text
Document
   ↓
First ~500-character chunk
   ↓
Next chunk with ~100-character overlap
   ↓
Next chunk
```

The exact boundaries can vary because `RecursiveCharacterTextSplitter` tries suitable separators rather than blindly cutting every 500 characters.

## Why chunk size matters

If chunks are too large:

```text
Large chunk
→ multiple topics mixed together
→ less precise retrieval
→ more tokens sent to LLM
```

If chunks are too small:

```text
Small chunk
→ may lose surrounding context
→ incomplete troubleshooting instructions
→ more fragments/vectors
```

We want a useful balance:

```text
Enough context
+
Focused meaning
+
Efficient retrieval
```

## Why do we use overlap?

Suppose an important troubleshooting instruction falls across a chunk boundary:

```text
Chunk 1:
...
Check the pod events to identify the
-------------------------------------

Chunk 2:
image pull failure and verify the image tag.
...
```

Without overlap, related information may be separated.

With overlap:

```text
Chunk 1:
Check the pod events to identify the
image pull failure...

Chunk 2:
identify the image pull failure and
verify the image tag...
```

Some context is preserved across the boundary.

Our configuration:

```text
chunk_size    = 500
chunk_overlap = 100
```

means neighboring chunks intentionally share some text.

## Chunking affects retrieval quality

Chunking is not just a storage operation.

It directly affects RAG quality:

```text
Document
 ↓
Chunking Strategy
 ↓
Embedding Quality / Granularity
 ↓
Retrieval Quality
 ↓
Context supplied to LLM
 ↓
Final Answer
```

Poor chunking can produce poor retrieval even when the embedding model and vector database are good.

## Kubernetes example

Suppose a runbook contains sections for:

```text
ImagePullBackOff
CrashLoopBackOff
OOMKilled
Pending Pods
```

Good chunking lets Qdrant retrieve the specific troubleshooting section relevant to the incident rather than sending the entire runbook.

For:

```text
Pod is OOMKilled
```

we want:

```text
OOMKilled troubleshooting chunk
```

rather than a large document containing several unrelated failure scenarios.

## Interview Answer

> **Chunking is the process of splitting large documents into smaller pieces before generating embeddings. In my Kubernetes RAG pipeline, I chunk troubleshooting runbooks before storing them in Qdrant so retrieval can return the specific section relevant to a problem instead of retrieving an entire large document. Chunk size needs to balance enough context with retrieval precision, and chunk overlap helps preserve context that crosses chunk boundaries. In our current implementation, we use RecursiveCharacterTextSplitter with a chunk size of 500 and an overlap of 100.**

## Remember

```text
Large Document
      ↓
   Chunking
      ↓
Focused Chunks
      ↓
  Embeddings
      ↓
    Qdrant
      ↓
More Precise Retrieval
```

In my Kubernetes RAG pipeline, I chunk troubleshooting runbooks before storing them in Qdrant so retrieval can return the specific section relevant to a problem instead of retrieving an entire large document. Chunk size needs to balance enough context with retrieval precision, and chunk overlap helps preserve context that crosses chunk boundaries. In our current implementation, we use RecursiveCharacterTextSplitter with a chunk size of 500 and an overlap of 100.**

# How Do We Choose Chunk Size and Chunk Overlap?

There is **no universal best chunk size**. We choose it based on document structure, the amount of context needed to answer a question, the embedding model, and retrieval quality.

Our current Kubernetes RAG configuration is:

```python
RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=100
)
```

## Chunk Size

Chunk size controls how much text goes into each chunk.

### If the chunk is too small

```text
Runbook:
"ImagePullBackOff can happen when the image tag is invalid.
Check Kubernetes events to identify the failure.
Then verify the image name and registry credentials."

Too-small chunks:

Chunk 1:
"ImagePullBackOff can happen..."

Chunk 2:
"Check Kubernetes events..."

Chunk 3:
"Then verify the image..."
```

Problems:

```text
Context becomes fragmented
Instructions may be separated
More vectors are created
Retrieved chunks may be incomplete
```

### If the chunk is too large

```text
One chunk:
ImagePullBackOff
+ CrashLoopBackOff
+ OOMKilled
+ Pending Pod
+ DNS troubleshooting
```

Problems:

```text
Multiple topics mixed together
Less precise embeddings/retrieval
More irrelevant text sent to LLM
Higher token usage
```

### Goal

Choose a chunk large enough to preserve a meaningful troubleshooting unit, but small enough to remain focused.

```text
Too small ←── useful focused chunk ──→ Too large
context loss                         topic dilution
```

## Chunk Overlap

Overlap repeats some content between neighboring chunks.

With:

```text
chunk_size = 500
chunk_overlap = 100
```

conceptually:

```text
Chunk 1:
[---------------- 500 ----------------]
                              [--100--]

Chunk 2:
                              [--100--]
                              [---------------- 500 ----------------]
```

The shared section helps preserve context when useful information crosses a boundary.

### Too little overlap

Can lose relationships across chunk boundaries.

### Too much overlap

Creates:

```text
Duplicate content
More embeddings
More storage
More repetitive retrieval results
More tokens passed to the LLM
```

Therefore overlap should be enough to preserve continuity, not duplicate most of the document.

## How Do We Choose Values in Production?

Do not choose chunk size only by guessing.

Start with a reasonable configuration based on the document structure, then evaluate retrieval using representative Kubernetes questions.

Example test queries:

```text
Why is nginx-app ImagePullBackOff?
Why was the pod OOMKilled?
Why is my pod stuck in Pending?
Why is the readiness probe failing?
```

Then measure whether the correct runbook sections appear in Top-K retrieval.

Compare configurations such as:

```text
Configuration A
chunk_size = 300
overlap = 50

Configuration B
chunk_size = 500
overlap = 100

Configuration C
chunk_size = 800
overlap = 150
```

Choose based on retrieval quality, not just chunk size itself.

Later, RAG evaluation can measure metrics such as retrieval relevance, Recall@K, MRR, and related metrics.

# What is Top-K Retrieval?

**Top-K retrieval means returning the K highest-ranked results from the vector search.**

In our Kubernetes RAG system, Qdrant may compare the query against many runbook chunks, but we do not send every matching chunk to the LLM.

We retrieve only the best K results.

## Our Current Configuration

```python
retriever = vectorstore.as_retriever(
    search_kwargs={"k": 3}
)
```

Here:

```text
K = 3
```

So the retriever returns the **top 3 results**.

## Kubernetes Example

Suppose the query is:

```text
Why is nginx-app ImagePullBackOff?
```

Qdrant searches the runbook vectors and ranks the results conceptually like this:

```text
1. ImagePullBackOff troubleshooting     0.92
2. Container registry troubleshooting  0.87
3. Invalid image tag troubleshooting   0.82
4. Kubernetes DNS troubleshooting      0.43
5. OOMKilled troubleshooting           0.31
```

With:

```text
K = 3
```

we retrieve:

```text
1. ImagePullBackOff troubleshooting
2. Container registry troubleshooting
3. Invalid image tag troubleshooting
```

The lower-ranked chunks are not returned.

The scores above are illustrative only.

## Why Not Retrieve Everything?

Sending every chunk to the LLM would cause:

```text
More irrelevant context
More tokens
Higher cost
Higher latency
More context-window usage
Potentially worse answers
```

Top-K keeps the context focused.

## What Happens if K is Too Small?

Suppose:

```text
K = 1
```

We retrieve only one chunk.

That may be enough for a simple question, but the answer may require information from multiple chunks, such as:

```text
Symptoms
+
Root causes
+
Troubleshooting steps
```

A very small K can reduce recall.

## What Happens if K is Too Large?

Suppose:

```text
K = 20
```

Now the LLM may receive many weakly related chunks.

That can cause:

```text
Noise
Irrelevant context
More tokens
Higher latency/cost
Potential confusion
```

So:

```text
Small K
→ focused context
→ risk of missing useful information

Large K
→ higher chance of finding useful information
→ more noise and tokens
```

## How Do We Choose K?

There is no universal best K.

We test representative Kubernetes queries and evaluate whether the required runbook information appears in the retrieved results.

Example:

```text
Why is the pod ImagePullBackOff?
Why was the pod OOMKilled?
Why is the pod Pending?
Why is readiness probe failing?
```

Then compare:

```text
K = 1
K = 3
K = 5
K = 10
```

Our current:

```text
K = 3
```

is a practical baseline, not a universal best value.

## Top-K vs Similarity Threshold

These solve different problems.

```text
Top-K
→ How many results should I return?

Similarity threshold
→ Is a result relevant enough to return?
```

Example:

```text
Top-K = 3
```

does not guarantee all three results are good.

If the knowledge base has no relevant document, Qdrant can still have nearest results.

This is why Top-K is often combined with relevance thresholds, filtering, reranking, or other retrieval controls.

## Top-K vs Top-K in LLM Sampling

Do not confuse RAG Top-K with LLM generation `top_k`.

```text
RAG Top-K
→ Number of retrieved documents/chunks

LLM top_k
→ Token-sampling parameter that restricts candidate next tokens
```

They are completely different concepts.

## Interview Answer

> Top-K retrieval means returning the K highest-ranked results from a retrieval search. In my Kubernetes RAG system, Qdrant ranks runbook chunks according to vector similarity with the query, and our retriever currently uses K=3, so the three highest-ranked chunks are returned to the LLM. A very small K can miss relevant context, while a very large K can introduce noise, increase token usage, latency, and cost. Therefore, K should be tuned using representative queries and retrieval evaluation rather than treated as a fixed universal value.
