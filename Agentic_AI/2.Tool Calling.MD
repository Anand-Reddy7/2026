# What is tool calling?

Tool calling is a mechanism that allows an LLM to request external functions or services to retrieve information or perform actions. The LLM itself doesn't execute the function; it generates a structured tool-call request containing the selected tool and its arguments, and the application or agent framework executes it and returns the result to the model. In my Kubernetes operations agent, I bind Kubernetes and RAG tools to the LLM. For example, the model can request get_pods, which is executed through MCP against the Kubernetes API. The result is returned to the LLM so it can continue reasoning based on actual cluster state.

# Tool Description ?

Docstring - Frameworks such as LangChain use it as part of the tool definition/schema exposed to the LLM.

Tool descriptions are important because the LLM uses the tool name, description and argument schema to understand what a tool does and when it should call it. Clear and specific descriptions improve tool selection and argument generation. However, tool descriptions are guidance for the model, not a security mechanism.

# How does an LLM decide which tool to call?

An LLM decides which tool to call by comparing the user's request and conversation context with the tool definitions/schema provided to the model.
The tool definition typically gives the model information such as:
```
Tool name
Tool description
Input parameters
Parameter types/descriptions
Required fields
```

The LLM then predicts whether it should answer directly or generate a structured tool call.

Interview Answer:

An LLM chooses a tool by reasoning over the user's request, conversation context, and the tool schemas provided to it. The schema tells the model the tool's name, description, parameters and expected argument types. Based on that information, the model can either generate a normal response or produce a structured tool-call request with the selected tool and arguments. In my Kubernetes agent, for example, a request for current pod status can cause the model to select get_pods, while an ImagePullBackOff diagnosis may lead it to call get_events and then search_book. The model proposes the tool call, but the application controls whether and how that tool is actually executed.

Better Tool Decision:

```
Clear tool names
        +
Specific descriptions
        +
Well-defined arguments
        +
Minimal overlap
        ↓
Better tool selection
```

# Does the LLM actually execute the function/tool?
No. The LLM itself normally doesn't execute the function. It generates a structured tool-call request containing the tool name and arguments. The agent framework or application receives that request, executes the actual function, and returns the result to the LLM so it can continue reasoning. 

In my Kubernetes agent, 
- the LLM can request get_pods, 
- LangGraph's ToolNode handles the tool execution, 
- the MCP layer communicates with the Kubernetes integration, and the result is returned to the LLM. 

For sensitive write tools, I intercept the request and require human approval before allowing execution.

# What does bind_tools() do?

In LangChain, bind_tools() makes a set of tool definitions available to the LLM so the model knows what tools it can request and what arguments those tools accept.

It does not execute the tools.

Then who will execute ?:

```py
tools = mcp_tools + [search_book]

tool_node = ToolNode(tools)                  // Execute actual tool calls from Model

model_with_tools = model.bind_tools(tools)   // Giving info to the model to generate tool call info
```

**Interview Answer:**

bind_tools() binds tool definitions to the LLM so that the model knows which tools are available, what each tool does, and what arguments it accepts. LangChain converts the tool definitions into the tool-calling schema expected by the model provider. The LLM can then return a structured tool-call request. bind_tools() itself doesn't execute the tool. In my Kubernetes agent, bind_tools() exposes the MCP and RAG tools to the model, while LangGraph's ToolNode executes the tool selected by the model.

# What information is contained in a tool schema?

A tool schema is the structured definition of a tool that tells the LLM what the tool does and how to request it correctly.

Typically, it contains:
```
Tool name + description + input parameters + parameter types + required fields/constraints.
```

For our Kubernetes agent, consider:
```
@tooldef get_pod_logs(namespace: str, pod_name: str) -> str:    
        """Get logs from a Kubernetes pod."""
```

Conceptually, the LLM receives a schema similar to:
```
{
  "name": "get_pod_logs",
  "description": "Get logs from a Kubernetes pod.",
  "parameters": {
    "type": "object",
    "properties": {
      "namespace": {
        "type": "string"
      },
      "pod_name": {
        "type": "string"
      }
    },
    "required": [
      "namespace",
      "pod_name"
    ]
  }
}
```

The exact provider representation can vary, but these concepts are the important ones.

# Why are tool names and descriptions important?
Tool names and descriptions are important because the LLM uses them to understand what each tool does and to decide which tool is appropriate for the user's request.
They are essentially the instructions that describe the capabilities available to the LLM.

In our Kubernetes agent, imagine these tools:
```
get_pods
get_pod_logs
get_events
get_nodes
search_book
update_deployment_image
```

The LLM needs to distinguish between them. Clear names and descriptions make that decision more reliable.

# What is a ToolMessage?
A ToolMessage represents the result of a tool execution and sends that result back into the LLM conversation so the model can reason about what the tool actually returned.
```
AIMessage.tool_calls = LLM requesting a tool.
ToolMessage = tool result being returned to the LLM.
```

# Why do we need tool_call_id?
tool_call_id uniquely correlates an LLM's tool request with the corresponding tool result. When the model generates a tool call, the provider assigns that invocation an ID. After the application executes the tool, the resulting ToolMessage includes the same ID so the model and framework know which result belongs to which request. This is particularly important when the model requests multiple tools. In my Kubernetes agent, LangGraph's ToolNode normally handles this automatically, while in my HITL rejection flow I explicitly create a ToolMessage using the original tool_call_id to indicate that the requested Kubernetes change was rejected.


# What happens when a tool throws an exception?
When a tool throws an exception, the tool execution has failed. A production agent should catch that failure and convert it into a useful observation so the LLM can understand what happened and decide what to do next.

The important principle is:
```
A tool failure should become an observation for the agent, not automatically crash the entire workflow.
```

# How do you prevent an LLM from calling dangerous tools?
The LLM can request a tool, but deterministic controls in the application should decide whether that request is allowed to execute.

- Expose only necessary tools
- Validate the arguments
- Human-in-the-loop for high-risk operations
- Restrict capabilities at the MCP server
        Security shouldn't exist only in LangGraph. Suppose somebody bypasses our approval routing and calls the MCP server directly. The MCP server should still expose only controlled operations.

        Intead of:

        execute_any_kubectl_command(command)

        we expose:

        get_pod_logs(namespace, pod_name)
        update_deployment_image(namespace)

This limits the agent's blast radius.
Even if the model behaves incorrectly, it only has the capabilities we've explicitly implemented.


# Tool vs Agent — what's the difference?
A tool performs a specific operation. An agent decides which operations are needed, uses tools, observes their results, and continues reasoning toward a goal.

# What makes our Kubernetes application agentic?
Our Kubernetes application is agentic because the LLM is not just answering a question—it can autonomously decide the next action, use tools, observe the result, and continue reasoning until it reaches the goal.
The core idea is:
```
Agentic = Goal → Reason → Act → Observe → Reason → Continue until completion
```

# What happens if the LLM chooses the wrong tool?
An LLM can choose the wrong tool because tool selection is probabilistic. For read-only tools, I generally allow the tool result to become an observation so the model can recognize that it wasn't useful and choose another tool. For example, if my Kubernetes agent requests pod logs for an ImagePullBackOff container and logs aren't available, that result can lead it to inspect Kubernetes events instead. For write operations, I don't rely on the LLM's decision: deterministic validation, policy checks and HITL prevent an incorrect tool selection from causing an infrastructure change. I also use step limits, timeouts and observability to prevent loops and evaluate tool-selection quality.

# Where should retries and timeouts be implemented?
I implement retries and timeouts at the layer that understands the failure rather than applying one global retry policy. LLM calls can retry transient provider failures such as rate limits or 5xx errors with bounded exponential backoff. MCP or tool code handles transient Kubernetes API/network failures and returns meaningful errors after exhausting its retry budget. Permanent errors such as 400, 403 or invalid input aren't blindly retried. At the LangGraph level, I use workflow-level fallbacks and execution limits rather than simply repeating every failed tool. For write operations, retries require extra care because a timeout doesn't prove the operation failed; I verify the actual Kubernetes state before retrying.

```
Transient failure → retry. Permanent failure → don't retry. Alternative approach available → fallback. Write outcome uncertain → verify before retrying.
```
