## 1. What is RAG, why is it needed, and how does it improve an AI agent?
RAG improves AI agents by retrieving relevant information from external knowledge sources and providing it to the LLM as context, helping generate more accurate, relevant, and grounded responses without retraining the model.

## 2. Explain the end-to-end RAG pipeline for your project, from ingestion to answer generation.
Our RAG pipeline ingests Kubernetes runbooks, splits them into chunks, generates OpenAI embeddings, stores them in Qdrant, retrieves the top 3 relevant chunks for each query, and passes them with MCP evidence to the LLM for grounded troubleshooting responses.

## 3. Why build a RAG pipeline instead of uploading documents directly to an LLM?
We build a RAG pipeline because LLMs have limited context windows, and sending entire documents with every request increases token usage, cost, and latency.
RAG solves this by splitting documents into chunks, generating embeddings, and storing them in a vector database.
When a user asks a question, we retrieve only the most relevant chunks and pass them to the LLM.
This makes the application more scalable, cost-effective, and easier to maintain as documents grow.

## 4. What is the difference between RAG and fine-tuning, and when would you choose each?
RAG and fine-tuning are two different approaches to improving LLM applications.
RAG retrieves relevant information from external knowledge sources and provides it to the LLM at runtime, without modifying the model's weights.
Fine-tuning trains an existing model on a specialized dataset to modify its behavior, response style, or task performance.
We choose RAG when we need up-to-date, organization-specific knowledge and fine-tuning when we need consistent behavior or specialized task performance.

## 5. What RAG architectures or patterns do you know?
The major RAG patterns are Naive RAG, Advanced RAG, Agentic RAG, Corrective RAG, Self-RAG, and Graph RAG. In our Kubernetes AI project, we use vector-based RAG integrated with LangGraph agents, and we can enhance retrieval accuracy using hybrid search, reranking, and corrective retrieval.

There are several RAG architectures, including Naive RAG, Advanced RAG, Agentic RAG, Corrective RAG (CRAG), Self-RAG, and Graph RAG.
Naive RAG follows a simple retrieve-and-generate approach. Advanced RAG improves retrieval using hybrid search, query rewriting, and reranking.
Agentic RAG uses AI agents to decide when and how to retrieve information. Corrective RAG and Self-RAG introduce evaluation and self-correction mechanisms to improve response quality.

| RAG Pattern | How it works | When to use |
|---|---|---|
| Naive RAG | Retrieve relevant chunks and generate an answer | Simple document Q&A |
| Advanced RAG | Uses query rewriting, hybrid search, reranking, and filtering | Improve retrieval accuracy |
| Agentic RAG | Agent decides when to retrieve, which tools to use, and what to do next | Complex troubleshooting workflows |
| Corrective RAG (CRAG) | Evaluates retrieved documents and corrects poor retrieval | When retrieval results are unreliable |
| Self-RAG | Uses self-evaluation to decide whether retrieval and generated answers are sufficiently supported | Improve answer grounding |
| Graph RAG | Uses knowledge graphs and relationships between entities | Multi-hop and relationship-based questions |
| Hybrid RAG | Combines keyword search (BM25) and semantic vector search | Queries containing both exact terms and semantic meaning |

## 7. What is cyclic/self-correcting RAG, and how does its correction loop terminate?
Cyclic RAG uses a feedback loop to evaluate and improve retrieval or generation. We terminate the loop when quality thresholds are met or when maximum retries, timeouts, or token budgets are reached, preventing infinite execution and unnecessary LLM costs.

Cyclic or Self-Correcting RAG is a RAG architecture where the system evaluates retrieved documents or generated answers and repeats retrieval when the quality is insufficient.
Instead of retrieving documents only once, it uses a feedback loop to improve the results through query rewriting, re-retrieval, or answer regeneration.
We terminate the correction loop using a maximum retry limit, quality thresholds, and timeout or token-budget limits.
If the system still cannot find reliable evidence, it returns an insufficient-evidence response or escalates for human investigation.


## 8. How would you implement a RAG system with AWS or other cloud services?
In our enterprise Kubernetes AI platform, we store source documents in Amazon S3 and embeddings in Qdrant. We use EventBridge Scheduler to trigger a Step Functions ingestion workflow every 12 hours.
The workflow compares S3 objects with document metadata maintained in PostgreSQL to identify new, modified, and deleted documents.
For new documents, we perform chunking, generate embeddings, and insert vectors into Qdrant. For modified documents, we index the new version and safely retire the old vectors. For deleted documents, we remove their associated vectors.
We also maintain synchronization status, retry failed documents, and monitor ingestion through CloudWatch.
This incremental synchronization approach avoids rebuilding the entire vector database and makes updated knowledge available to our Kubernetes agents without redeploying the application."
One important enterprise improvement: A 12-hour schedule means deleted or sensitive documents may remain retrievable until the next successful sync. ## What heppens if only few lines modified in the RAG Document ??
In our KubePilot AI RAG pipeline, when a troubleshooting document changes, our ingestion service regenerates embeddings for the affected chunks and upserts them into Qdrant.
HNSW does not randomly place the updated vectors. It organizes graph connections based on vector similarity. If the semantic meaning changes slightly, the updated vector may retain similar neighbors; if the meaning changes significantly, its nearest neighbors can change.
Qdrant manages the necessary index updates internally, so we don't manually modify HNSW graph edges.

## 11. How do you recover from a document ingestion failure without reprocessing everything?
In our enterprise KubePilot AI platform, I would implement incremental ingestion with checkpointing, idempotency, and retry mechanisms.
We maintain document versions, processing status, and synchronization checkpoints in PostgreSQL. When ingestion fails, we identify the failed document and resume from its last successful processing stage instead of restarting the entire ingestion job.

**Example:**
Suppose our scheduled ingestion detects 1,000 documents, but only 80 have changed.
We process those 80 documents. If 5 fail during embedding, PostgreSQL records their last successful stage.
When the retry workflow starts, it resumes those 5 documents from the appropriate checkpoint. The other 75 completed documents are skipped, and the remaining 920 unchanged documents are never reprocessed.

## 15. How do you manage updated documents, old embeddings, version IDs, and automated deletion/upsert?
In our enterprise KubePilot AI platform, I would implement incremental document synchronization with version tracking and idempotent Qdrant upserts.

## How do we prevent race conditions?
We prevent race conditions using document version tracking and conditional updates in PostgreSQL. Before activating a newly indexed document, we verify that its version is still the latest known version. If an older ingestion job finishes late, PostgreSQL rejects its activation. We also delete embeddings using document ID and version ID so old cleanup jobs cannot remove newer versions.

### Simple example
Suppose k8s-troubleshooting.pdf is stored in S3.
```
8:00 AM
Document version v2 is uploaded.
Ingestion Job A starts processing v2.
Processing takes 10 minutes.

8:05 AM
Document is updated again to v3.
Ingestion Job B starts processing v3.

8:08 AM
Job B finishes processing v3.

8:10 AM
Job A finishes processing v2.
```
Problem: If Job A blindly updates PostgreSQL at 8:10 AM, it might change the active version from v3 back to v2.
Our Insight Agent could then retrieve outdated troubleshooting instructions.

### How do we prevent this?
We maintain two fields in PostgreSQL:
```
| Field | Meaning |
|---|---|
| latest_version | Latest version detected in S3 |
| active_version | Version currently used for RAG retrieval |
```

For example, at 8:10 AM:
```
latest_version = v3
active_version = v3

Job A wants to activate v2.

Check:
Is v2 == latest_version?

No!

Reject activation of v2.
```

This check must happen atomically in PostgreSQL so another job cannot change the desired version between checking and updating.

## 16. What is chunking, why does chunk size matter, and what are the trade-offs between small and large chunks?
Chunking is the process of splitting large documents into smaller, meaningful pieces before generating embeddings and storing them in a vector database.
Chunk size matters because it directly affects retrieval accuracy, context preservation, embedding cost, and LLM token consumption.
Small chunks provide more precise retrieval but may lose important context. Large chunks preserve more context but can introduce irrelevant information and increase token usage.
For our enterprise KubePilot AI platform, I would prefer structure-aware recursive chunking, with parent-child retrieval for complex troubleshooting documents, and tune chunk sizes using retrieval evaluation metrics.


## 17. Which chunking strategies are available, and which have you used?
There are several chunking strategies in RAG, including fixed-size, recursive, semantic, document-structure-aware, and parent-child chunking.

For a large-scale, multi-agent Kubernetes platform, I would choose structure-aware recursive chunking combined with parent-child retrieval.
This is because Kubernetes runbooks contain headings, error codes, commands, troubleshooting steps, and tables. We need to preserve these relationships while retrieving relevant information.

## 18. Why choose recursive chunking instead of fixed-size chunking?
would prefer recursive chunking over fixed-size chunking because it preserves meaningful text boundaries.
Fixed-size chunking splits documents based on a predefined character or token count, which can break sentences, troubleshooting steps, or related information.
Recursive chunking first tries to split by paragraphs, then lines, then spaces, and finally smaller units when necessary.
This helps preserve context and improves the chances of retrieving complete troubleshooting information from Qdrant.

We would evaluate these configurations using a golden dataset of Kubernetes troubleshooting questions and metrics such as Recall@K, Precision@K, answer faithfulness, latency, and token usage.
Based on the evaluation results, we would choose the configuration that provides the best balance of retrieval quality and cost

## 21. What are embeddings, and how are they used in RAG?
Embeddings are numerical representations of text that capture its semantic meaning. In our KubePilot AI platform, we use embeddings to identify relevant Kubernetes troubleshooting documents even when the user's question does not contain the exact keywords.
During document ingestion, we convert runbook chunks into embeddings and store them in Qdrant. When a user asks a question, we generate its embedding using the same model and perform similarity search to retrieve relevant chunks

Embeddings convert text into numerical vectors that represent semantic meaning. In our KubePilot AI platform, we generate embeddings for Kubernetes runbook chunks and store them in Qdrant. When a user asks a question, we convert it into an embedding using the same model and retrieve similar chunks through vector similarity search. The Insight Agent then passes these chunks to the LLM to generate a grounded troubleshooting response. This allows us to retrieve relevant knowledge even when the question and document use different terminology.

## How does Qdrant find relevant documents?
Qdrant finds relevant documents using vector similarity search. During ingestion, we convert document chunks into embeddings and store them in Qdrant.
When a user asks a question, we generate an embedding for that question using the same embedding model.
Qdrant searches for the closest document vectors using a similarity metric such as cosine similarity. It commonly uses an HNSW index to make this search efficient, even with millions of vectors.
Finally, Qdrant returns the Top-K matching chunks along with their similarity scores and metadata.

## What is cosine similarity and how it will calculate ?
Cosine similarity is a mathematical technique used to measure how similar two vectors are based on the angle between them.
It is calculated by taking the dot product of two vectors and dividing it by the product of their magnitudes. The dot product means multiplying corresponding vector values and adding them together.
In our KubePilot AI RAG application, we convert Kubernetes runbook chunks into embeddings and store them in Qdrant. When a user asks a question, we generate its embedding using the same model.
Qdrant uses cosine similarity to identify the document vectors closest in direction to the query vector. A higher similarity score generally indicates greater semantic similarity.
Qdrant also uses HNSW indexing to efficiently search millions of vectors without comparing every vector individually.
Finally, Qdrant returns the Top-K relevant chunks, which our Insight Agent passes to the LLM to generate a grounded troubleshooting response.

## 30. How do you choose between cosine similarity, dot product, and Euclidean distance, and why is cosine similarity called that?
Cosine similarity, dot product, and Euclidean distance are mathematical methods used to compare vectors in a vector database.
- Cosine similarity measures the angle between two vectors, focusing on their direction rather than their magnitude. It is commonly used for text embeddings and semantic search.
- Dot product multiplies corresponding vector values and adds them together. It considers both direction and magnitude, so it is useful when the embedding model is designed for dot-product scoring.
- Euclidean distance measures the straight-line distance between two vectors. It is useful when the actual distance between points is meaningful, such as in certain image or numerical feature applications.

| Method | What It Measures | Best Use Case |
|---|---|---|
| Cosine Similarity | Angle between vectors | Text embeddings and semantic search |
| Dot Product | Direction and magnitude | Models trained for dot-product scoring |
| Euclidean Distance | Straight-line distance | Numerical features and distance-based retrieval |

## 38. How do you choose candidate Top-K and final Top-K values?

## 39. What do you do when retrieved results or reranker confidence scores are low?
In our enterprise KubePilot AI platform, when Qdrant retrieval scores or reranker scores are low, we don't immediately send those chunks to the LLM and allow it to generate an answer.
Instead, we implement a Corrective RAG (CRAG) workflow using LangGraph.
First, we evaluate whether the retrieved chunks are relevant to the user's question. If relevance is low, we rewrite the query, expand the search, or switch to hybrid retrieval using BM25 and vector search.
We then rerank the new candidates and check their relevance again.

## 43. What is hallucination, how do you detect it, and how do you prevent an LLM from answering beyond retrieved evidence?
In our enterprise KubePilot AI platform, hallucination is especially dangerous because an incorrect Kubernetes diagnosis could lead to production incidents.
To detect hallucinations, we evaluate faithfulness and factual correctness. We extract factual claims from the generated answer and verify whether they are supported by retrieved Qdrant runbooks or live Kubernetes MCP tool results.
To prevent hallucinations, we implement grounded generation, mandatory source citations, retrieval relevance checks, and a Corrective RAG workflow.
If retrieved evidence is insufficient, the agent can rewrite the query, perform hybrid search, or invoke authorized MCP tools to verify the live cluster state.

For production-changing actions, we additionally enforce deterministic validation, least-privilege tool permissions, and human approval.
