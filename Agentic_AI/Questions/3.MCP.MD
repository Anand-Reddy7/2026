## What is MCP and why we need to use it ?

MCP stands for Model Context Protocol. It is an open standard that allows AI agents to connect with external tools, APIs, databases, and other systems through a standardized interface.
Without MCP, we may need to build separate integrations for different tools and AI applications.
MCP provides a common way to discover and invoke tools, making integrations reusable and easier to maintain.

## Diff b/w MCP Vs FastMCP

MCP is the protocol that standardizes AI-to-tool communication, whereas FastMCP is a Python framework that makes implementing MCP servers and clients easier.


MCP (Model Context Protocol) is an open standard that defines how AI applications communicate with external tools, resources, and prompts.
FastMCP is a Python framework that simplifies building MCP servers and clients.
MCP defines the communication standard, while FastMCP provides an implementation of that standard.

| MCP | FastMCP |
|---|---|
| Open protocol/standard | Python framework |
| Defines communication between MCP clients and servers | Simplifies implementing MCP clients and servers |
| Defines tools, resources, prompts, and communication mechanisms | Provides decorators and Python APIs |
| Language-independent | Python-based |
| Specifies how MCP works | Helps developers build MCP integrations |

## How does FastMCP maintain context between multiple requests?
FastMCP provides request and session context for tool execution, but persistent conversation memory must be managed separately using LangGraph checkpointing or external storage like Redis or PostgreSQL

## 2. What is FastMCP middleware?
FastMCP middleware intercepts tool requests and responses to implement centralized logging, security, rate limiting, and monitoring using the call_next() mechanism.

FastMCP middleware is a component that intercepts MCP requests and responses before and after tool execution. It is used to implement common functionality such as logging, authentication, authorization, rate limiting, error handling, and monitoring

```py
from fastmcp import FastMCP
from fastmcp.server.middleware import Middleware, MiddlewareContext

mcp = FastMCP("kubernetes-operations")

class LoggingMiddleware(Middleware):

    async def on_call_tool(self, context: MiddlewareContext, call_next):
        print("Tool execution started")

        result = await call_next(context)

        print("Tool execution completed")
        return result

mcp.add_middleware(LoggingMiddleware())

@mcp.tool()
def get_pods(namespace: str) -> str:
    return f"Fetching pods from {namespace}"
```

## 3. What happens if `call_next` is not called in FastMCP middleware?
If call_next() is not called, the request does not proceed to the next middleware or tool. We use this behavior to block unauthorized or invalid requests before execution.

```
Authorized request: call_next() executes the Kubernetes tool.
Unauthorized request: Middleware raises an error, and the Kubernetes tool is not executed.
```

## 4. How do you handle an LLM selecting the wrong MCP tool?
We prevent incorrect MCP tool execution through clear tool descriptions, strict schemas, role-based tool restrictions, validation, and HITL approval for sensitive operations.

Example Suppose the user asks:
```
"Why is my nginx pod failing?"
The LLM incorrectly selects update_deployment_image instead of get_pod_logs.

We handle this through:

1. Tool restrictions: Insight Agent can access only read-only tools such as get_pods, get_pod_logs, and get_events.
2. Tool descriptions: Clearly explain when each tool should be used.
3. Validation: Check tool name, parameters, and permissions before execution.
4. HITL: Require approval for production-changing operations.
5. Retry: Return a structured error so the agent can select the correct tool, with a bounded retry limit.
```

## 5. How do you troubleshoot latency when multiple agents call the same MCP tool?

I troubleshoot MCP latency using LangSmith and OpenTelemetry traces to identify bottlenecks, then optimize concurrent requests through caching, asynchronous execution, connection management, and rate limiting.

When multiple agents call the same MCP tool, latency can occur due to concurrent requests, API rate limits, connection bottlenecks, or slow backend responses.
I would use LangSmith and OpenTelemetry to trace individual tool calls and identify where the delay occurs.
Based on the findings, I would optimize API calls, introduce caching for read-only operations, configure concurrency limits, and use asynchronous execution where appropriate.

1. Trace requests	Use LangSmith/OpenTelemetry to measure MCP tool latency
2. Identify bottleneck	Check MCP server processing time versus Kubernetes API response time
3. Check concurrency	Look for connection limits, queueing, or blocking synchronous calls
4. Optimize requests	Cache repeated read-only results with a short TTL
5. Control load	Apply concurrency limits, timeouts, and rate limiting
6. Monitor	Track p50, p95, p99 latency, error rates, and concurrent requests

## 6. How do you handle MCP tool invocation failures or schema-validation errors?
We handle MCP tool failures using input validation, exception handling, retry policies, and fallback mechanisms.
For schema-validation errors, we return a clear error message to the agent so it can correct the tool parameters and retry.
For temporary failures like network timeouts or API unavailability, we use bounded retries with exponential backoff.
If retries fail, we log the error, trace it using LangSmith, and route the workflow to a fallback or escalation path.

## Remote Vs Local MCP Server

or local MCP servers, we generally use stdio transport, where the client starts the server as a subprocess. For remote MCP servers, we use Streamable HTTP transport, where the client connects through an HTTP endpoint. Both use the same MCP protocol and support tool discovery and invocation.

We can connect to an MCP server using different transports.
For a local MCP server, we commonly use stdio, where the MCP client starts the server as a subprocess and communicates through standard input and output.
For a remote MCP server, we use Streamable HTTP, where the MCP client connects to the server through an HTTP endpoint.
Both approaches follow the same MCP protocol. The main difference is how the client and server communicate.

```py
from fastmcp import Client
from fastmcp.client.transports import StdioTransport

transport = StdioTransport(
    command="python",
    args=["kubernetes_mcp_server.py"]
)

async with Client(transport) as client:
    tools = await client.list_tools()
    result = await client.call_tool(
        "get_pods",
        {"namespace": "default"}
    )
    print(result)
```

from fastmcp import Client

## How do you secure an MCP server?
We secure MCP servers using authentication, authorization, RBAC, least-privilege access, input validation, and secure communication.
For remote MCP servers, we use OAuth 2.1-based authorization where applicable and HTTPS/TLS for secure communication.
We validate tool inputs, restrict access to sensitive tools, and implement Human-in-the-Loop (HITL) approval for critical operations.
We also use middleware for security checks, audit logging, rate limiting, and monitoring.

## What is MCP architecture?
MCP (Model Context Protocol) follows a Host–Client–Server architecture.
The MCP Host is the AI application, such as a LangGraph-based agent application.
The MCP Client runs inside the host and manages communication with MCP servers.
The MCP Server exposes tools, resources, and prompts that allow AI agents to interact with external systems.

## What is the difference between stdio, SSE, and Streamable HTTP transports?
MCP supports different transports for communication between MCP clients and servers.

stdio is mainly used for local MCP servers, where the client starts the server as a subprocess and communicates through standard input and output.
SSE is a legacy HTTP-based transport used for remote MCP servers, where the server sends events to the client through a persistent SSE connection.
Streamable HTTP is the modern recommended transport for remote MCP servers. It supports HTTP requests and responses, with optional SSE streaming.

## How do you prevent prompt injection, tool poisoning, and unauthorized tool execution in MCP?

We secure MCP tool execution using input validation, trusted tool definitions, RBAC, least-privilege permissions, and Human-in-the-Loop (HITL) approval.
We treat tool responses and external data as untrusted, so the LLM cannot use instructions embedded in logs or documents to bypass security policies.
We also restrict which MCP tools each agent can access and enforce authorization at the MCP server before executing sensitive operations.

## What is the difference between MCP and A2A (Agent-to-Agent) protocol?
MCP (Model Context Protocol) is used to connect AI agents with external tools, APIs, databases, and resources.
A2A (Agent-to-Agent) is a protocol that enables independent AI agents to communicate, delegate tasks, and collaborate with each other.
MCP focuses on Agent-to-Tool communication, whereas A2A focuses on Agent-to-Agent communication.
