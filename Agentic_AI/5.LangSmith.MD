# LangSmith

For AI observability, I use LangSmith with the LangGraph-based Kubernetes agent. It gives end-to-end traces across the Supervisor and specialized agents, LLM calls, RAG retrieval and tool execution. This helps me debug why an agent selected a particular workflow, what Kubernetes evidence and runbook context it used, and where latency or failures occurred. I also use it for evaluation datasets to test retrieval and generation quality. I keep infrastructure observability separate using Prometheus/Grafana and OpenTelemetry—LangSmith observes the AI workflow, while Prometheus and Grafana observe the Kubernetes platform and applications.

```
Prometheus/Grafana help you observe Kubernetes and application behavior; LangSmith helps you observe and evaluate the AI/agent workflow.
```


**When something goes wrong, normal application logs alone make questions like these difficult:**
```
Why did the Supervisor select the Insight Agent?
Which MCP tools were called?
What arguments were passed?
Which RAG documents were retrieved?
How long did the LLM take?
How many tokens were consumed?
Why did the agent recommend that remediation?
```

# How LangSmith capture the traces??

LangChain and LangGraph have built-in tracing instrumentation. When LangSmith tracing is enabled through environment configuration, the framework's callback/tracing infrastructure automatically captures supported LLM, chain, graph and tool executions and sends the trace data to LangSmith using the configured API key. Therefore I get basic end-to-end tracing without manually adding tracing code. I add custom instrumentation only when I need application-specific metadata or spans.


**You probably configured environment variables along these lines:**
```
LANGSMITH_TRACING=true
LANGSMITH_API_KEY=<your-key>
LANGSMITH_PROJECT=kubepilot-ai

Note: Enable LangSmith tracing for supported LangChain/LangGraph operations.
```


# What are P50, P95 and P99 latency?

They are latency percentiles. P50 is the median latency, meaning 50% of requests complete within that value. P95 means 95% complete within that value, and P99 means 99% complete within that value. I use P50 to understand normal performance and P95/P99 to identify tail-latency problems.

```
P50 = 3 sec
P95 = 8 sec
P99 = 15 sec
```

## Example

Use a 100-request example in an interview. It makes P50/P95/P99 very easy to explain.

Suppose we execute our Kubernetes troubleshooting agent 100 times and record the end-to-end latency. First, sort all 100 latency values from fastest to slowest:

```
Request position after sorting:

1    → 1.0 sec
2    → 1.1 sec
...
50   → 3.0 sec    ← P50
...
95   → 7.0 sec    ← P95
...
99   → 12.0 sec   ← P99
100  → 25.0 sec
```

So you can explain:

```
- P50 = 3 sec → roughly 50% of requests completed within 3 seconds.
- P95 = 7 sec → roughly 95% completed within 7 seconds; about 5% were slower.
- P99 = 12 sec → roughly 99% completed within 12 seconds; about 1% was slower.
- The slowest request was 25 seconds, so P99 is not the maximum.
```

```
Normal:

P50 = 3 sec
P95 = 6 sec
P99 = 8 sec

Problem:

P50 = 3 sec
P95 = 7 sec
P99 = 25 sec
                   ↑
              investigate
```

Here P50 hasn't changed, so normal requests are still fast. But P99 jumped from 8 to 25 seconds, meaning a small percentage of requests became very slow. If P99 suddenly increases, I filter or inspect the slow traces and identify whether the delay came from the LLM, MCP tool, RAG retrieval, or another agent step.
