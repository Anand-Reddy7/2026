## 1. RAG Pipeline: Can you explain the end-to-end RAG pipeline architecture implemented in your project, including document ingestion, chunking, embeddings, vector storage, retrieval, reranking, and response generation?

In our **KubePilot AI project**, we implemented a RAG architecture to help our Kubernetes troubleshooting agents retrieve relevant operational knowledge and generate evidence-based responses.

Our RAG pipeline consists of two major stages: 
**1. document ingestion**
**2. query retrieval**.

**Document Ingestion**
In the ingestion pipeline, we collect Kubernetes runbooks, SOPs, troubleshooting documentation, and historical incident reports. We preprocess these documents and split them into meaningful chunks using token-aware and section-based chunking.

We then generate embeddings using **OpenAI's text-embedding-3-small** and store the vectors in **Qdrant**, along with metadata such as document source, Kubernetes version, and document type.

**Query Retrieval**.
During the retrieval phase, when a user asks a troubleshooting question, we generate the query embedding using the same embedding model and perform similarity search in Qdrant.

We initially retrieve the **Top 20 relevant chunks** and apply **BGE Reranker V2 M3** to select the **Top 5 most relevant chunks**.

We then construct the LLM context using these retrieved chunks while managing the token budget to avoid unnecessary token consumption.

Since KubePilot AI is an Agentic AI application, we also integrate **Kubernetes MCP tools** to retrieve live pod status, logs, and events.

Our **LangGraph agent combines the retrieved runbooks with live Kubernetes evidence and passes this context to GPT-5.5** for root-cause analysis and remediation recommendations.

To improve retrieval performance, we use Qdrant's HNSW-based approximate nearest-neighbor indexing, metadata filtering, and reranking. We monitor the pipeline using LangSmith and OpenTelemetry and evaluate retrieval quality using Recall@K and NDCG.

We also support incremental document updates so that changes to runbooks don't require reindexing the entire knowledge base.

**Overall, our RAG pipeline combines historical operational knowledge with real-time Kubernetes data to help agents perform accurate, grounded, and safe troubleshooting.**


```py
# Data Ingestion Pipeline

# KubePilot AI - RAG Data Ingestion

EMBEDDING_MODEL = "text-embedding-3-small"
CHUNK_SIZE = 500
CHUNK_OVERLAP = 50

def ingest_documents(documents):

    for document in documents:

        # 1. Load document
        text = load_document(document)

        # 2. Clean and preprocess
        cleaned_text = preprocess(text)

        # 3. Token-aware, section-based chunking
        chunks = split_into_chunks(
            cleaned_text,
            chunk_size=CHUNK_SIZE,
            chunk_overlap=CHUNK_OVERLAP
        )

        # 4. Generate embeddings
        for chunk in chunks:

            vector = generate_embedding(
                model=EMBEDDING_MODEL,
                text=chunk.text
            )

            # 5. Store vector and metadata in Qdrant
            qdrant.upsert(
                collection="kubernetes_runbooks",
                id=chunk.id,
                vector=vector,
                payload={
                    "text": chunk.text,
                    "source": document.source,
                    "document_type": document.type,
                    "k8s_version": document.k8s_version
                }
            )

    return "Ingestion completed"


# Data Retrival Pipeline
EMBEDDING_MODEL = "text-embedding-3-small"
RERANKER_MODEL = "BAAI/bge-reranker-v2-m3"
LLM_MODEL = "gpt-5.5"

TOP_K = 20
FINAL_TOP_K = 5
MAX_CONTEXT_TOKENS = 3000


def retrieve_documents(user_query, filters):

    # 1. Convert user query to embedding
    query_vector = generate_embedding(
        model=EMBEDDING_MODEL,
        text=user_query
    )

    # 2. Similarity search in Qdrant
    candidates = qdrant.search(
        collection="kubernetes_runbooks",
        vector=query_vector,
        top_k=TOP_K,
        metadata_filter=filters
    )

    # 3. Rerank retrieved documents
    reranked_chunks = rerank(
        model=RERANKER_MODEL,
        query=user_query,
        documents=candidates
    )

    # 4. Select top 5 chunks
    top_chunks = reranked_chunks[:FINAL_TOP_K]

    # 5. Build context within token budget
    context = build_context(
        chunks=top_chunks,
        max_tokens=MAX_CONTEXT_TOKENS
    )

    return {
        "context": context,
        "sources": extract_sources(top_chunks)
    }


def rag_pipeline(user_query, filters):

    # 6. Retrieve relevant documents
    rag_result = retrieve_documents(
        user_query=user_query,
        filters=filters
    )

    # 7. Construct prompt with retrieved context
    prompt = f"""
    You are a Kubernetes troubleshooting assistant.

    Use the retrieved Kubernetes runbooks and
    troubleshooting documentation to answer
    the user's question.

    Retrieved Context:
    {rag_result["context"]}

    User Question:
    {user_query}

    Instructions:
    1. Answer based on retrieved context.
    2. Identify possible root causes.
    3. Provide troubleshooting steps.
    4. Cite relevant runbook sources.
    5. If information is insufficient, say so.
    6. Do not execute remediation actions.
    """

    # 8. Call GPT-5.5 with retrieved context
    response = llm.invoke(
        model=LLM_MODEL,
        prompt=prompt
    )

    # 9. Return generated answer with sources
    return {
        "answer": response,
        "sources": rag_result["sources"]
    }


# 10. Example execution
result = rag_pipeline(
    user_query="Why is my Kubernetes pod getting OOMKilled?",
    filters={"document_type": "runbook"}
)

print(result["answer"])
print(result["sources"])
```


## 2. Agent Evaluation: How do you evaluate the performance, accuracy, reliability, and safety of your AI agents? Explain your approach to offline evaluations, online production evaluations, and sampling-based evaluations.

## Agent Evaluation — KubePilot AI

In our **KubePilot AI — Kubernetes Operations Agent Platform**, we evaluate the complete agent workflow rather than just the final LLM response. Our evaluation focuses on **accuracy, reliability, performance, and safety**.

We organize our evaluation strategy into two main categories: **Offline Evaluations and Online Production Evaluations**, with sampling-based evaluation as part of our online evaluation strategy.

### 1. Offline Evaluations (Before Deployment)

For offline evaluation, we prepare a **golden dataset** containing real-world Kubernetes troubleshooting scenarios such as OOMKilled, CrashLoopBackOff, ImagePullBackOff, and deployment failures.

Each test case contains the user query, simulated or historical Kubernetes evidence, expected MCP tool calls, relevant runbooks, verified root cause, and expected safety behavior.

We evaluate the agent using the following metrics:

- **Task Success Rate:** Measures whether the agent successfully completes the troubleshooting workflow and produces the expected outcome.
- **Tool Selection Accuracy and Execution Success Rate:** Verifies whether the agent selects the appropriate Kubernetes MCP tools, executes them correctly, and handles tool failures.
- **RAG Retrieval Quality:** Uses Recall@K and NDCG to measure whether the relevant Kubernetes runbooks are retrieved and ranked correctly from Qdrant.
- **Root Cause Accuracy:** Checks whether the agent's diagnosis matches the verified incident root cause.
- **Faithfulness / Groundedness:** Evaluates whether the generated response is supported by retrieved runbooks and actual Kubernetes evidence, without hallucinations.
- **Safety Compliance:** Verifies whether the agent follows access-control policies, avoids unauthorized operations, and requests human approval before sensitive remediation actions.

We run these evaluations as **regression tests** whenever we change prompts, LLM models, RAG configurations, MCP tools, or LangGraph workflows.

### 2. Online Evaluations (Production)

In production, we use **LangSmith and OpenTelemetry** to capture end-to-end agent execution traces, including LangGraph workflow steps, MCP tool calls, RAG retrieval results, LLM responses, and execution latency.

We continuously monitor:

- **Reliability:** Task completion rate, MCP tool success/failure rates, and workflow errors.
- **Performance:** End-to-end latency, p95/p99 response times, and latency at individual workflow stages.
- **Cost:** Input/output token consumption and LLM inference cost.
- **Response Quality:** Groundedness, relevance, and reasoning quality using LLM-as-a-Judge evaluations.
- **Safety:** Unauthorized tool attempts, approval-policy violations, and potentially unsafe remediation recommendations.

For response quality, we can use **LLM-as-a-Judge**, where a separate evaluation call assesses whether the agent's answer is relevant, supported by the available evidence, and consistent with the expected troubleshooting behavior.

However, LLM-as-a-Judge alone cannot confirm the actual root cause. We also use engineer feedback and confirmed incident outcomes to validate diagnostic accuracy.

### 3. Sampling-Based Evaluations (Part of Online Evaluation)

Running LLM-based quality evaluations for every production request can increase cost. Therefore, we can implement a **sampling-based evaluation strategy**.

For example:

- **10% of normal production executions:** Randomly selected for LLM-based quality evaluation.
- **100% of failed or high-risk executions:** Selected for additional evaluation and investigation.
- **100% of production requests:** Subject to mandatory authorization, policy validation, and safety enforcement.

These are illustrative sampling rates that can be adjusted based on production traffic, cost, and risk.

We run quality evaluations **asynchronously using background workers**, so they do not increase user-facing response latency.

We also ensure that the random sample represents different incident types, environments, and agent versions, rather than evaluating only failures.

### 4. Continuous Improvement and Feedback Loop

Whenever we identify incorrect diagnoses, MCP tool failures, hallucinations, or performance degradation in production, we investigate the corresponding LangSmith traces.

We identify whether the issue originated from **RAG retrieval, tool execution, agent orchestration, or LLM reasoning**.

Once the issue is resolved, we add the scenario to our golden dataset and rerun offline regression tests to prevent similar failures in future releases.

### Conclusion

**Offline Evaluations** validate agent behavior before deployment using golden datasets and predefined expected outcomes.

**Online Evaluations** continuously monitor real-world agent accuracy, reliability, performance, and safety, while **sampling-based evaluations** help control evaluation costs.

By combining offline testing, production observability, LLM-as-a-Judge, human feedback, and continuous regression testing, we improve the reliability, accuracy, safety, and cost-efficiency of our KubePilot AI agents.


## 3. SDLC Agent Architecture: How would you design and implement an Agentic AI solution to automate the Software Development Life Cycle (SDLC), from requirement analysis and code generation to testing, code review, and deployment?

I would design an **Agentic AI-powered SDLC automation platform using Python, FastAPI, LangGraph, MCP, RAG, and GPT-5.5**, with specialized agents handling different stages of the development lifecycle.

The workflow starts when a developer submits a Jira ticket or GitHub issue through FastAPI.

**LangGraph acts as the central orchestrator**, coordinating specialized agents such as Requirement Analysis, Code Analysis, Code Generation, Testing, Code Review, and DevOps agents.

First, the Requirement Analysis Agent retrieves the Jira ticket through MCP and extracts requirements and acceptance criteria.

Next, the Code Analysis Agent inspects the existing GitHub repository and uses RAG to retrieve relevant architecture documentation, coding standards, and historical implementation knowledge from Qdrant.

The Code Generation Agent then generates or modifies code in an isolated development branch.

The Testing Agent executes unit and integration tests. If tests fail, LangGraph routes the failure details back to the Code Generation Agent for correction, with bounded retries.

Once testing passes, the Code Review Agent checks code quality, security vulnerabilities, coding standards, and requirement coverage. Any review failures are routed back for correction.

After successful validation, the DevOps Agent creates a pull request with the code changes and test results.

**Human approval is mandatory before merging or deploying sensitive changes.** Once approved, the existing CI/CD pipeline handles building, scanning, testing, and deployment.

Finally, the DevOps Agent monitors the deployment, verifies application health, and updates the Jira ticket with the execution status.

For production reliability, I would implement **LangGraph checkpointing, RBAC, isolated code execution, bounded retries, audit logging, and human-in-the-loop approvals**.

I would use **LangSmith and OpenTelemetry** for end-to-end tracing, performance monitoring, and debugging.

Overall, this architecture automates repetitive SDLC activities while keeping developers in control of critical decisions and maintaining code quality, security, and deployment reliability.


## 4. Golden Dataset: What is a golden dataset in Agentic AI evaluation? How did you prepare, validate, and maintain the golden dataset for your KubePilot AI application?

In our **KubePilot AI project**, a golden dataset is a collection of predefined Kubernetes troubleshooting scenarios with verified expected outcomes. We use it mainly for **offline evaluation and regression testing** of our Agentic AI workflows.

Since our application uses LangGraph, MCP tools, and RAG, we evaluate not just the final LLM response but the complete agent execution.

**First, to prepare the dataset**, we collect historical Kubernetes incidents, troubleshooting runbooks, and postmortems covering scenarios such as OOMKilled, CrashLoopBackOff, ImagePullBackOff, and deployment failures.

For each test case, we define the user query, Kubernetes evidence, expected MCP tool calls, relevant runbooks, verified root cause, and expected safety behavior.

For example, if a pod is restarting because of an OOMKilled event, the agent should retrieve the relevant pod status, logs, and events, identify the memory-related issue using the available evidence, retrieve the appropriate runbook, and recommend safe remediation without making unauthorized changes.

**Second, for validation**, we review the expected outcomes against confirmed incident reports and involve Kubernetes engineers or SREs to verify the correctness of root causes, expected tool usage, and safety requirements.

We also label relevant runbook chunks so that we can evaluate retrieval quality using Recall@K and NDCG.

**Third, for evaluation**, we execute our LangGraph agent against the golden test cases and compare the actual results with the expected outcomes.

We measure task success rate, tool selection accuracy, RAG retrieval quality, root-cause accuracy, groundedness, and safety compliance.

**Finally, for maintenance**, we version the golden dataset and update it whenever we introduce changes to prompts, models, MCP tools, or agent workflows.

We also analyze production failures using LangSmith traces, validate the actual incident outcomes, and add those scenarios to the golden dataset for future regression testing.

**Overall, the golden dataset acts as our trusted evaluation baseline, helping us detect regressions and continuously improve the accuracy, reliability, and safety of our KubePilot AI agents.**

## 5. Real-World Production Challenges: What were the major technical challenges or production issues you encountered while developing and deploying your Agentic AI application? How did you investigate, troubleshoot, and resolve them?

In our **KubePilot AI — Kubernetes Operations Agent Platform**, the major technical challenges we focused on were **RAG retrieval accuracy, Kubernetes MCP tool reliability, LLM hallucinations, agent execution latency, and safe remediation**.

**The first challenge was RAG retrieval quality.** Sometimes the agent could retrieve irrelevant or outdated Kubernetes runbooks, leading to inaccurate troubleshooting recommendations.

To investigate, we examined LangSmith traces, verified the Qdrant retrieval results, checked metadata filters and document versions, and analyzed whether the relevant runbooks were present in the retrieved Top-K chunks.

We addressed this through improved document chunking, metadata filtering, runbook updates, and retrieval tuning. We evaluated improvements using Recall@K and NDCG.

**The second challenge was MCP tool reliability.** Kubernetes tool calls could fail due to incorrect namespaces, insufficient RBAC permissions, API errors, or unavailable resources.

We investigated the failed MCP calls using execution traces and Kubernetes API error messages. We addressed these issues through parameter validation, appropriate service-account permissions, error handling, and fallback behavior in LangGraph.

**The third challenge was LLM hallucination and root-cause accuracy.** In some scenarios, the agent could generate a confident diagnosis without sufficient Kubernetes evidence.

We improved grounding by combining retrieved runbooks with live MCP tool outputs, requiring evidence-based reasoning, and instructing the agent to clearly distinguish confirmed root causes from possible causes.

**The fourth challenge was agent execution latency.** Since our workflows involve multiple MCP calls, RAG retrieval, reranking, and LLM invocations, overall response time can increase.

We used LangSmith and OpenTelemetry to identify latency bottlenecks across individual workflow stages. We optimized retrieval parameters, controlled context token usage, and reduced unnecessary tool and LLM calls.

**The fifth challenge was safe Kubernetes remediation.** Since our agents can interact with live infrastructure, we needed to prevent unauthorized or risky operations.

We addressed this through Kubernetes RBAC, least-privilege MCP tools, validation of remediation actions, and human-in-the-loop approvals for sensitive changes.

**Our overall troubleshooting approach was to inspect end-to-end traces, identify whether the issue originated from RAG, MCP tools, LangGraph orchestration, or LLM reasoning, apply the appropriate fix, and validate it against our golden dataset before release.**

This approach helps improve the accuracy, reliability, performance, and safety of our Agentic AI application.


## 6. Pre-Production vs. Production Troubleshooting: Suppose your RAG or Agentic AI application works correctly in the pre-production environment but produces incorrect results or experiences performance issues in production. How would you systematically debug and identify the root cause, step by step?

In our **KubePilot AI project**, if the RAG or Agentic AI application works correctly in pre-production but produces incorrect responses or performance issues in production, I follow a systematic, layer-by-layer debugging approach.

**First, I reproduce the issue** using the same query in both environments and compare the responses, configurations, and execution behavior.

**Second, I inspect LangSmith and OpenTelemetry traces** to identify exactly where the execution differs, whether it's document retrieval, reranking, LLM reasoning, MCP tool execution, or LangGraph orchestration.

**Third, I verify the RAG pipeline.** I compare the Qdrant collection, document ingestion status, chunk counts, metadata filters, and embedding configurations between environments.

I also verify that both environments use compatible versions of `text-embedding-3-small` and that the correct runbooks are available in production.

**Fourth, I analyze retrieval and reranking.** I check whether the relevant runbook appears in the initial Top 20 Qdrant results and whether the BGE reranker selects it in the final Top 5.

If the correct document is missing during retrieval, I investigate indexing, filters, and embedding compatibility. If retrieval is correct but the final response is wrong, I investigate the prompt, context construction, and GPT-5.5 configuration.

**Fifth, I verify MCP tool execution and LangGraph workflows.** I check Kubernetes API permissions, namespaces, service-account RBAC, tool failures, routing decisions, and workflow state.

**Sixth, if the issue is performance-related**, I analyze stage-level latency using OpenTelemetry, including Qdrant retrieval time, reranking time, MCP tool latency, LLM response time, and production resource utilization.

This helps identify whether the problem is caused by infrastructure load, API throttling, excessive tool calls, or large LLM context.

**Finally, once I identify the root cause**, I apply the fix, validate it against our golden dataset, and compare retrieval accuracy, task success, and latency before deploying the correction.

I also add the production failure scenario to our offline regression dataset to prevent recurrence.

**Overall, my approach is to compare environments, inspect execution traces, isolate the failing component, validate the fix, and continuously monitor production behavior.**

The key principle is that I don't immediately assume the LLM is the problem. I first verify whether the correct evidence was retrieved, passed through the agent workflow, and provided to the model.

## 7. Agent-to-Agent (A2A) Protocol: What is the Agent-to-Agent (A2A) protocol? How does it enable communication and collaboration between independent AI agents, and how does it differ from LangGraph-based multi-agent orchestration and the Model Context Protocol (MCP)?

A2A, or Agent-to-Agent Protocol, is an open protocol that enables independent AI agents to discover each other's capabilities, communicate, delegate tasks, and collaborate, even when they are developed using different frameworks or deployed as separate services.

The main purpose of A2A is to provide standardized communication between autonomous agents without exposing their internal implementation.

A2A supports Agent Cards for capability discovery, structured task delegation, task lifecycle management, and exchanging messages and artifacts.

For example, in our KubePilot AI project, we use LangGraph to orchestrate Kubernetes troubleshooting workflows and MCP to connect our agents with Kubernetes tools such as pod status, logs, and events.

If we wanted to integrate an independently deployed Security Analysis Agent, we could use A2A to delegate security analysis tasks to that agent.

The Security Agent would execute the task using its own framework and tools, then return its findings to KubePilot AI. Our LangGraph workflow would combine those findings with Kubernetes troubleshooting results.

# LangChain

LangChain is an open-source framework for building Generative AI and LLM-powered applications. It provides reusable components for prompt management, model integration, RAG, embeddings, vector databases, retrievers, tool calling, and structured outputs.

Its main advantage is that it reduces boilerplate code and simplifies connecting LLMs with external data and enterprise systems.

In our Kubernetes AI platform, we use LangChain for LLM integrations, RAG pipelines, and tools, while LangGraph manages the complex agent workflows.

# Lang Graph
LangGraph is a graph-based orchestration framework for building stateful Agentic AI applications. It uses nodes to execute tasks, edges to control execution, and shared state to maintain information across the workflow.

Its key advantages are conditional routing, loops, checkpointing, human-in-the-loop approvals, and multi-agent orchestration.

In our KubePilot AI project, we use LangGraph to coordinate Kubernetes troubleshooting workflows involving LLM reasoning, RAG retrieval, MCP tool execution, and controlled remediation.

## Core components of LangGraph

| Component | Purpose |
|---|---|
| State | Stores and shares information between nodes |
| Nodes | Python functions that execute tasks |
| Edges | Define execution flow between nodes |
| Conditional Edges | Dynamically select the next node |
| StateGraph | Defines the graph and its shared state |
| START / END | Entry and exit points |
| Checkpointer | Persists execution state for resuming workflows |
| Interrupts | Pause execution for human approval or external input |
| Reducers | Control how state updates are merged |
| Subgraphs | Organize reusable workflows within larger graphs |

## Why use LangGraph instead of writing normal Python functions?

You can build workflows using ordinary Python. LangGraph becomes valuable when you need:

- **Dynamic routing:** Decide the next action based on previous results.
- **Cycles:** Repeat investigation until sufficient evidence is collected.
- **State management:** Share and update data across workflow steps.
- **Checkpointing:** Save progress and resume interrupted execution.
- **Human-in-the-loop:** Pause before risky operations and resume after approval.
- **Multi-agent orchestration:** Coordinate specialized agents and their responsibilities.

## How Agents can communicate each other ?
In LangGraph, agents primarily communicate through shared graph state and controlled execution flow.

Each agent is represented as a node or subgraph. When one agent executes, it reads the current state, performs its task, and returns state updates. The next agent receives the updated state and continues processing.

LangGraph supports multiple communication patterns, including supervisor-based routing, agent handoffs using Command, subgraphs, and parallel execution.

In our Kubernetes Agentic AI platform, the Kubernetes Agent retrieves live infrastructure information using MCP tools, the RAG Agent retrieves relevant documentation, and the Analysis Agent combines these results using shared LangGraph state.

## LangGraph Vs A2A
LangGraph and A2A are complementary technologies.

LangGraph is used to orchestrate multiple agents within an application using shared state, nodes, conditional edges, and checkpointing.

A2A is a protocol that allows independently developed and deployed agents to discover each other's capabilities, delegate tasks, and exchange results, even when they use different frameworks.

For example, in our KubePilot AI platform, we use LangGraph to coordinate Kubernetes, RAG, and Analysis agents. If we need to communicate with a Security AI Agent owned by another team and deployed as an independent service, we can use A2A.

MCP is used to access external tools, LangGraph handles internal orchestration, and A2A supports communication between independent agent applications.


# MCP

MCP stands for Model Context Protocol. It is an open standard that allows AI applications to connect with external tools, data sources, and services using a standardized client-server architecture.

MCP servers expose capabilities such as tools, resources, and prompts. MCP clients discover these capabilities and invoke them through standardized protocol messages.

## Core Components of MCP

| Component | Purpose |
|---|---|
| MCP Host | AI application that manages MCP client connections |
| MCP Client | Communicates with an MCP server |
| MCP Server | Exposes tools, resources, and prompts |
| Tools | Executable operations such as `get_pods()` |
| Resources | Data or contextual information exposed by a server |
| Prompts | Reusable prompt templates exposed by a server |
| Transport | Communication mechanism, such as stdio or Streamable HTTP |
| JSON-RPC | Message format used for MCP communication |
| Tool Discovery | Allows clients to discover available server tools |
| Authorization | Controls access where supported and configured |

## MCP Resources
An MCP Resource is a way for an MCP server to expose data or information that an AI application can read.

Think of resources as readable information, such as configuration files, documentation, runbooks, or cluster details

```py
from fastmcp import FastMCP

mcp = FastMCP("Kubernetes Server")

@mcp.resource("config://cluster")
def get_cluster_config() -> str:
    return """
    Cluster: production-cluster
    Namespace: payments
    Environment: production
    Region: ap-south-1
    """

if __name__ == "__main__":
    mcp.run()

Here:
- @mcp.resource() exposes information as an MCP resource.
- config://cluster is the resource URI.
- The MCP client can read it using resources/read.
```

## MCP Prompts
An MCP Prompt is a reusable prompt template exposed by an MCP server.

Instead of writing the same troubleshooting instructions repeatedly inside different AI applications, you can define them once on the MCP server.

## Why MCP Prompt instead of a hardcoded system prompt?
Suppose three applications need the same troubleshooting procedure:
- KubePilot AI web application
- DevOps chatbot
- Incident management assistant
Instead of maintaining separate copies of the instructions, all three can retrieve the standardized troubleshooting prompt from the MCP server.

This provides reusable and centrally maintained prompt templates. Each application still decides whether and how to use them.

## How LLM discover the tools ?
MCP tool discovery happens through the tools/list JSON-RPC method. After establishing and initializing a connection, the MCP Client sends a tools/list request to the MCP Server. The server responds with available tool names, descriptions, and input schemas. The client can cache these definitions and refresh them when the tool list changes.

## How to restrict the tool execution by other teams?

In MCP, we can implement team-based tool access using authentication and RBAC.

When an MCP client connects, we validate the user's identity using OAuth or JWT and identify their team membership.

During tools/list, we expose only the tools authorized for that team. During tools/call, we validate authorization again before executing the operation.

For example, in our Kubernetes platform, developers can retrieve pod logs, but only DevOps engineers can restart deployments.

We also enforce Kubernetes RBAC as an additional security layer.


# RAG
RAG stands for Retrieval-Augmented Generation. It is an architecture that improves LLM responses by retrieving relevant information from external knowledge sources and adding that information to the prompt before generating an answer.

We use RAG because LLMs do not automatically know our organization's private documentation, internal procedures, or recently updated knowledge.

In our KubePilot AI project, we use RAG with Qdrant to retrieve Kubernetes troubleshooting runbooks, incident resolutions, and operational documentation.

When a user reports a Kubernetes issue, the Kubernetes Agent retrieves live cluster information using MCP tools, while the RAG Agent retrieves relevant troubleshooting knowledge from Qdrant.

The Analysis Agent combines both sources to provide evidence-based root-cause analysis and remediation recommendations.

## How do we measure whether our RAG is actually retrieving correctly?
This is especially important for interviews.

We should maintain a test dataset containing real Kubernetes questions and their expected relevant documents.

| Metric | What It Measures |
|---|---|
| Recall@K | Whether the correct documents appear among the top K results |
| Precision@K | How many retrieved results are actually relevant |
| MRR | How early the first relevant document appears |
| NDCG@K | Whether highly relevant documents rank near the top |
| Faithfulness / Groundedness | Whether the generated answer is supported by the context |
| Answer Correctness | Whether the answer matches verified facts or expected outcomes |

For example, if you test 100 Kubernetes troubleshooting questions and the relevant document appears in the top 5 for 90 of them, the Hit Rate@5 is 90%.

That does not automatically mean Recall@5 is 90%, because a question may have multiple relevant documents.

## What is Checkpointer and why we need it ?
In LangGraph, a Checkpointer is used to save the state of an agent workflow so that execution can be resumed later without starting from the beginning.

It is especially important for multi-agent systems, human-in-the-loop workflows, and long-running tasks

## Agent State ?
Agent State in LangGraph is a structured data object that maintains information throughout an agent workflow.

It allows multiple agents to share information without directly calling each other.

Each agent receives the current state, performs its operation, and returns updates that LangGraph merges into the state.

## How to handle upsert effectively when a single file modified in 1000 files ? Did you replace entire chunks ?
In our KubePilot AI project, we use an incremental indexing approach to handle document updates efficiently.

For example, if we have 1,000 Kubernetes runbooks and only 5 lines change in one runbook, we don't reprocess all 1,000 documents.

First, we identify the modified document using file hashes or version information. Then we split the updated document into chunks and compare their content hashes with the previously indexed chunks.

We generate new embeddings only for the modified or newly added chunks and upsert those points into Qdrant. Unchanged chunks remain untouched, and obsolete chunks are deleted.

We prefer section-based chunking with stable identifiers because fixed-size chunking can cause multiple chunk boundaries to shift even when only a few lines change.

This approach reduces unnecessary embedding generation, improves indexing efficiency, and keeps our RAG knowledge base updated without rebuilding the entire collection.

## How do you evaluated your Agent ?
In our **KubePilot AI — Kubernetes Operations Agent Platform**, we follow two types of evaluations: **Offline Evaluations and Online Production Evaluations**. We evaluate the complete agent workflow rather than just the final LLM response.

### 1. Offline Evaluations (Before Deployment)

We prepare a golden test dataset containing Kubernetes incident scenarios such as OOMKilled, CrashLoopBackOff, ImagePullBackOff, and deployment failures, along with their expected outcomes.

We evaluate the agent using multiple metrics:

- **Task Success Rate:** Whether the agent successfully completes the troubleshooting workflow.
- **Tool Selection Accuracy and Execution Success Rate:** Whether the agent selects and executes the correct MCP tools.
- **RAG Retrieval Quality:** We use Recall@K and NDCG to measure whether relevant runbooks are retrieved from Qdrant.
- **Root Cause Accuracy:** Whether the agent correctly identifies the underlying Kubernetes issue.
- **Faithfulness / Groundedness:** Whether the response is supported by retrieved runbooks and actual Kubernetes evidence.
- **Safety Compliance:** Whether the agent follows authorization policies and human approval requirements.

We use these evaluations as regression tests before deploying changes to prompts, agent workflows, or LLM configurations.

### 2. Online Evaluations (Production)

In production, we use **LangSmith and OpenTelemetry** to capture agent execution traces, including MCP tool calls, RAG retrieval results, LLM responses, and execution latency.

We continuously monitor metrics such as **tool execution success rate, task completion, p95/p99 latency, token usage, and execution cost**.

For response quality, we use **LLM-as-a-judge** to evaluate groundedness, relevance, and reasoning quality.

Since evaluating every production request using an LLM can be expensive, we can implement **sampling-based evaluations**, where:

- **10% of normal production requests** are selected for LLM-based quality evaluation.
- **100% of failed or high-risk executions** are selected for evaluation.
- **100% of requests** undergo mandatory authorization and safety enforcement.

These quality evaluations run asynchronously to avoid increasing user-facing latency.

We also collect engineer feedback and compare agent diagnoses against confirmed incident outcomes to evaluate actual root-cause accuracy.

If we identify incorrect responses, tool failures, or quality degradation, we investigate the LangSmith traces and add those scenarios to our offline regression dataset.

**Overall, Offline Evaluations help us validate the agent before deployment, while Online Evaluations help us continuously monitor and improve agent quality in production. This ensures our agents are accurate, reliable, safe, and cost-efficient.**
