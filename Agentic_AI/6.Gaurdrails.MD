# Gaurdrails

Guardrails are security, safety, and policy controls that validate and restrict what an AI application can accept, generate, and execute.
In a traditional backend application, we validate user inputs, enforce authentication, check authorization, and validate business rules.
In an Agentic AI application, we need those same controls, but we also have additional risks because an LLM can interpret instructions, select tools, and initiate actions

Example:

Suppose the LLM decides to execute:
```
kubectl delete deployment payment-service -n production
```

That is a destructive operation the user never authorized.
Guardrails should prevent the agent from executing this action without appropriate authorization and approval.
A key principle is that guardrails must be enforced by trusted application code, not just by asking the LLM to behave safely.


## Types of Guardrails in Agentic AI

| Type | Purpose | KubePilot AI Example |
|---|---|---|
| Input Guardrails | Validate incoming requests | Detect malicious or unauthorized instructions |
| Prompt-Injection Defenses | Treat external content as untrusted | Ignore instructions embedded in retrieved runbooks |
| Retrieval Guardrails | Restrict knowledge access | Retrieve only documents authorized for the user |
| Tool-Execution Guardrails | Control agent actions | Block unauthorized Kubernetes deletion |
| Output Guardrails | Validate generated responses | Prevent secrets from appearing in responses |
| Human-in-the-Loop (HITL) | Require approval for sensitive operations | Approve production deployment restarts |
| Resource Guardrails | Control cost and execution | Limit agent steps, tokens, and tool calls |


## Interview-ready answer: What are guardrails in Agentic AI?

```
In an Agentic AI system, guardrails are security, safety, and governance controls that ensure AI agents operate within defined policies and permissions.
In our KubePilot AI architecture, we apply guardrails at multiple layers, including user input validation, retrieval access control, tool authorization, human approvals, and output validation.
For example, our Automation Agent interacts with Kubernetes through custom MCP tools. Before executing any operational action, we validate the user's identity, role, target namespace, and requested operation.
Read-only actions such as retrieving pod logs can be permitted automatically, while sensitive operations such as restarting or deleting production workloads require explicit authorization and, where configured, human approval.
We also treat RAG documents and tool responses as untrusted content to reduce prompt-injection risks.
Finally, we apply output validation to prevent sensitive information leakage and maintain audit logs for agent decisions and tool executions.
The key principle is that the LLM can recommend actions, but trusted application policies control what actually gets executed.
```
