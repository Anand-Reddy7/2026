# What is an LLM?

An LLM (Large Language Model) is an AI model trained on a very large amount of text and code to learn patterns in language. At runtime, its fundamental job is to predict the next token based on the tokens already in the context.

Interview Answer:

An LLM, or Large Language Model, is a deep-learning model, typically based on the Transformer architecture, trained on large amounts of text and code. It learns statistical relationships between tokens and generates output by predicting tokens based on the input context. By itself, an LLM has limitations such as lack of real-time system knowledge and possible hallucinations, so in our Kubernetes agent we combine the LLM with RAG for external knowledge and MCP tools for live cluster information and actions.

# What is inference?

Inference means using an already-trained AI/ML model to produce an output for new input.

Interview Answer:

Inference is the process of using a trained model to generate predictions or outputs for new input without retraining the model. In an LLM application, whenever we send a prompt or conversation context to the model and receive generated text or a tool call, that model execution is inference.


```text
| Training | Inference |
|---|---|
| Model learns | Model uses what it learned |
| Updates model weights | Normally doesn't update weights |
| Requires large datasets | Requires an input/prompt |
| Computationally very expensive | Usually much cheaper |
| Done before serving the model | Happens when users/applications call the model |
```

# What is a token?

A token is a small unit of text that an LLM reads and generates.
A token is not necessarily one word. Depending on the tokenizer, a token can represent a whole word, part of a word, punctuation, whitespace, or another text fragment.

Interview answer:

A token is the basic unit of text processed by an LLM. A token can be a word, part of a word, punctuation, or another text fragment depending on the tokenizer. The input is converted into tokens before inference, and the model generates output token by token. Token count is important because it affects context-window limits, latency, and cost.

```text
Input:
"Kubernetes pods are failing"

        ↓ Tokenizer

["Kubernetes", " pods", " are", " failing"]

        ↓

4 tokens (illustrative)
```

```
System instructions       → tokens
Previous conversation     → tokens
User question             → tokens
Tool results              → tokens
RAG runbook chunks         → tokens
                            -------
                            Context
```

Why tokens are important in production:

```
Tokens
 ├── Context-window usage
 ├── Cost
 └── Latency
```

If we blindly send huge Kubernetes logs, many RAG chunks, and the entire conversation history to the model, token usage can become unnecessarily large.

That's why production agents need things like log truncation, good RAG retrieval, Top-K control, conversation summarization, and context management.


# What is a context window?

A context window is the maximum amount of information, measured in tokens, that an LLM can consider within a model request.

Interview answer:

A context window is the maximum amount of tokenized information an LLM can process within a request. It can include system instructions, conversation history, the current user prompt, RAG context and tool results. If the context becomes too large, the application needs strategies such as trimming, summarization or retrieval. Context-window management is important for controlling latency, cost and maintaining relevant context.

Think of it as the LLM's working space during inference:
```
                CONTEXT WINDOW
┌─────────────────────────────────────┐
│ System instructions                 │
│ Previous conversation               │
│ User's current question             │
│ RAG retrieved chunks                │
│ Tool calls / tool results           │
│ Other supplied context              │
│                                     │
│ + generated output (model-dependent │
│   token accounting)                 │
└─────────────────────────────────────┘
```

Why does the context window matter?

Imagine, just for illustration, a model supports a 100,000-token context window.

```
If we provide:
System instructions          2,000
Conversation history        30,000
Kubernetes logs             40,000
RAG chunks                  20,000
Current question             1,000
                           --------
                            93,000 tokens
```

We're already close to the limit.

This is why we shouldn't simply dump huge Kubernetes logs into our agent.

# What happens when context becomes too large?

Interview answer:
```
When the input exceeds an LLM's context-window limit, the request cannot be processed as-is and must be reduced, or it may be rejected. Even before reaching the hard limit, excessive context increases token cost and latency and can introduce irrelevant information. In an agentic application, I manage this using techniques such as RAG Top-K retrieval, log filtering and truncation, conversation trimming or summarization, and sending only relevant state to the model.
```

When the context becomes too large, there are two different problems to understand:

1. It can exceed the model's context-window limit
Suppose, purely as an example:
Model context limit = 100K tokens
```
System prompt        =   5K
Chat history         =  40K
Kubernetes logs      =  35K
RAG context          =  15K
Current request      =   8K
                       ----
Total                = 103K ❌
```

The request no longer fits.
Depending on the model/API/framework, the request may be rejected for exceeding the context limit, or the application/framework may need to truncate/reduce the input before sending it.

2. Even before reaching the hard limit, too much context can hurt
A request might technically fit but still contain too much irrelevant information.
For example:
User:
"Why is nginx-app in ImagePullBackOff?"
```
Context sent:
├── 100 previous messages
├── thousands of log lines
├── old pod information
├── unrelated runbooks
└── current cluster information

Possible consequences include:
More tokens
   ↓
Higher cost
   ↓
Higher latency

Too much irrelevant context
   ↓
Important information harder to use
   ↓
Potentially poorer answer quality
```
So a large context window doesn't mean we should fill it.

# What is temperature?

Temperature is an LLM generation parameter that controls how random or deterministic the model's token selection is.

Interview answer:
```
Temperature is a generation parameter that controls randomness in an LLM's token selection. Lower temperature makes outputs more deterministic by favoring higher-probability tokens, while higher temperature increases diversity by giving lower-probability tokens more chance of being selected. For an operational agent such as our Kubernetes troubleshooting agent, I would generally prefer low temperature because consistency is more important than creativity. However, low temperature alone does not prevent hallucination, so grounding and tool validation are still required.
```

Remember that an LLM generates text by predicting probabilities for possible next tokens.

**Another Answer:**

Think of temperature as controlling how willing the LLM is to choose a less-likely next token.
Suppose the model receives:
```
"The capital of France is"
```

Before temperature is applied, imagine the model has calculated these next-token probabilities:
```
Paris       90%
Lyon         5%
Marseille    3%
London       2%
```

Temperature changes the shape of this probability distribution before sampling.

**Low temperature — more deterministic :**
```
Say:
temperature = 0.1
```

The distribution becomes much more concentrated around the highest-probability token, conceptually:
```
Paris       99.9%
Lyon         0.05%
Marseille    0.03%
London       0.02%
```

So repeated requests are very likely to continue with:
```
Paris
```

That's why low temperature is useful for things such as factual Q&A, RAG, structured extraction, and many agent/tool workflows.

**Higher temperature — more variation :**
```
Suppose:
temperature = 1.5
```

Conceptually, the probabilities become flatter:
```
Paris       65%
Lyon        15%
Marseille   12%
London       8%
```

Temperature changes how strongly the model favors the higher-probability choices.

**Low temperature:**

With a low temperature, the model tends to favor the most probable tokens.
```
Low temperature
      ↓
Less randomness
      ↓
More predictable / consistent output
```

This is useful for tasks where you want stable, factual behavior.

In our project:

```py
Conceptually:
model = ChatOpenAI(    
    model="gpt-5.4",    
    temperature=0)
```

Notes:
- Temperature does not guarantee correctness.
- Even with temperature 0, an LLM can hallucinate.

That's why our architecture still uses:
```
LLM
 ├── MCP → actual Kubernetes state
 ├── RAG → runbook knowledge
 └── HITL → protect write operations
 ```

```py
def get_temperature(task_type):
    if task_type == "factual":
        return 0.1

    if task_type == "coding":
        return 0.2

    if task_type == "brainstorming":
        return 0.8

    if task_type == "creative":
        return 1.0
```

# What causes hallucinations?

Interview answer:


Hallucination occurs when an LLM generates plausible but unsupported or incorrect information. This happens because an LLM predicts tokens based on learned patterns rather than querying a guaranteed source of truth. Hallucinations can be caused by missing or ambiguous context, stale knowledge, poor RAG retrieval, noisy context, or incomplete tool results. In my Kubernetes agent, I reduce this by grounding current-state questions through MCP tools against the Kubernetes API, using RAG for runbook knowledge, validating tool results, and requiring human approval for write operations.


Hallucination is when an LLM generates information that sounds plausible and confident but is incorrect, unsupported, or fabricated.
The fundamental reason is that an LLM is a next-token prediction system, not a truth database.
```
Prompt
  ↓
LLM predicts likely next tokens
  ↓
Produces fluent response
  ↓
Fluent does NOT necessarily mean factua
```

What causes hallucinations?

A few causes are especially important for interviews:
1. Missing knowledge or information. If you ask our plain LLM, “Which pods are failing in my IBM Kubernetes cluster right now?”, the model has no live cluster state. If forced to answer without a tool, it may invent something.
2. Insufficient or ambiguous context. A question like “Why is the application failing?” doesn't tell the model which application, namespace, pod, error, or timeframe. The model may fill in missing details based on patterns.
3. Incorrect or irrelevant RAG context. RAG does not automatically eliminate hallucination. If Qdrant retrieves unrelated chunks, the LLM can generate an answer based on bad evidence.
```
Bad query/retrieval
      ↓
Wrong chunks
      ↓
LLM
      ↓
Wrong grounded-looking answer
This is why our pending similarity threshold, metadata filtering, and RAG evaluation are important.
```
4. Stale information. The model's learned knowledge or an old runbook may not represent the current environment. For current Kubernetes state, we therefore use MCP tools against the actual cluster.
5. Very large/noisy context. If we send huge logs, long conversation history, and many unrelated runbook chunks, important evidence can get buried among irrelevant information.
6. Tool failures or incomplete tool results. Suppose get_pod_logs fails but the model continues as though it received logs. Unless we handle errors properly and instruct the agent to distinguish observed facts from assumptions, it can generate an unsupported diagnosis.
7. Generation randomness. Higher temperature can increase variability and potentially increase unsupported outputs in some situations. But temperature is not the fundamental cause of hallucination, and setting temperature=0 does not eliminate it.

# How would you reduce hallucination in an operations agent?

For an **operations agent**, such as our Kubernetes troubleshooting
agent, I would reduce hallucination mainly by ensuring the LLM **doesn't
rely on its own knowledge when authoritative data is available**.

## Core approach

``` text
User
 ↓
LLM / Agent
 ↓
1. Live data → MCP tools
2. Knowledge → RAG/Qdrant
3. Validate tool results
4. Restrict context
5. Structured outputs
6. HITL for changes
7. Evaluation/monitoring
```

## 1. Ground current-state answers using tools

If the user asks, **"Which pods are failing?"**, the model should not
answer from its internal knowledge.

``` text
User question
     ↓
LLM
     ↓
get_pods
     ↓
MCP
     ↓
Kubernetes API
     ↓
Actual pod status
     ↓
LLM answer
```

For operational information such as pods, nodes, logs, events,
deployments, and services, the **Kubernetes API is the source of
truth**.

## 2. Ground troubleshooting knowledge using RAG

If the agent finds `OOMKilled`, it can retrieve the relevant runbook:

``` text
OOMKilled
   ↓
search_book
   ↓
Qdrant
   ↓
OOMKilled runbook
   ↓
Relevant chunks
   ↓
LLM
```

This grounds the diagnosis in our organization's runbooks. RAG alone is
not enough: poor retrieval can still produce a bad answer. Similarity
thresholds, metadata filtering, hybrid search, and RAG evaluation help
improve retrieval quality.

## 3. Never hide tool failures

If `get_pod_logs()` returns a Kubernetes API error, the agent should not
behave as though logs were successfully retrieved.

Return an explicit observation such as:

``` text
Unable to retrieve logs because the container
has not started successfully.
```

The model should distinguish:

``` text
Observed:
  logs unavailable

NOT:
  logs showed X
```

The distinction between **observed facts and assumptions** is extremely
important in operations.

## 4. Control what context reaches the LLM

Don't send everything to the model.

Instead of:

``` text
50,000 log lines
+ entire chat history
+ every runbook
+ every event
         ↓
        LLM
```

use:

``` text
Relevant logs
+ relevant events
+ Top-K RAG chunks
+ relevant conversation
         ↓
        LLM
```

This reduces noisy and conflicting information while also controlling
token usage.

## 5. Use structured outputs where appropriate

For workflows that need programmatic validation, require structured
output instead of arbitrary free-form text.

``` json
{
  "resource": "nginx-app",
  "namespace": "ai-agent-lab",
  "observed_state": "ImagePullBackOff",
  "probable_cause": "Invalid image tag",
  "evidence": [
    "Container waiting reason: ImagePullBackOff"
  ],
  "recommended_action": "Update image"
}
```

The application can validate these fields before taking action.

## 6. Never treat LLM-generated actions as facts

If the model proposes changing the nginx image, that is a **proposal**,
not permission to execute.

``` text
LLM recommendation
       ↓
HITL
       ↓
Human approval
       ↓
MCP write tool
       ↓
Kubernetes API
       ↓
Verify resulting state
```

HITL does not itself prevent hallucination. It prevents an incorrect
model decision from automatically becoming a production change.

## 7. Verify after performing an action

Don't assume an accepted API request means the problem is fixed.

``` text
update_deployment_image()
        ↓
Kubernetes API accepts update
        ↓
get deployment / pods
        ↓
verify rollout/state
        ↓
report actual result
```

An API accepting an update does **not** necessarily mean the application
is healthy.

## Interview Answer

> **In an operations agent, I reduce hallucination by grounding the
> model rather than relying solely on its internal knowledge. For
> current infrastructure state, I use tools connected to the source of
> truth---for example, my Kubernetes agent uses MCP tools to query the
> Kubernetes API. For troubleshooting knowledge, I use RAG over our
> runbooks in Qdrant. I also explicitly propagate tool failures, limit
> irrelevant context, use structured outputs and validation where
> appropriate, and require human approval for write operations. After an
> action, I query the system again to verify the actual state rather
> than trusting the LLM's assumption that the action succeeded.**

## Key Principle

> **For operational agents, the LLM should reason over authoritative
> observations rather than invent the state of the system.**


# Why shouldn't an LLM be trusted directly for Kubernetes changes?

An LLM should **not be given unrestricted permission to make Kubernetes
changes directly** because an LLM is a probabilistic reasoning system,
not a deterministic control system. It can misunderstand a request,
hallucinate information, select the wrong tool, or generate incorrect
parameters.

For production infrastructure, we therefore treat an LLM's proposed
change as an **intent or recommendation**, not automatically as an
authorized action.

## 1. LLMs can hallucinate

Suppose the user says:

> Fix the nginx application.

The LLM might conclude:

``` text
Problem: ImagePullBackOff
Solution: Change image to nginx:latest
```

But that doesn't automatically mean `nginx:latest` is the correct
approved image.

The model may have insufficient information or make an incorrect
assumption.

``` text
LLM recommendation ≠ verified infrastructure change
```

## 2. The LLM may misunderstand user intent

Consider:

> Check whether nginx needs to be restarted.

That does **not** mean:

> Restart nginx.

If the LLM is allowed to execute unrestricted changes, misunderstanding
natural language could modify production infrastructure.

A safer workflow is:

``` text
User request
    ↓
LLM interprets request
    ↓
Inspect cluster
    ↓
Propose action
    ↓
Human approval
    ↓
Execute
```

## 3. Tool arguments can be wrong

Even when the model chooses the correct tool, it could generate
incorrect arguments.

For example:

``` text
update_deployment_image(
    namespace="production",
    deployment_name="nginx-app",
    container_name="nginx",
    image="nginx:latest"
)
```

Perhaps the intended namespace was:

``` text
staging
```

The function call itself may be perfectly valid while the **decision
behind the arguments is wrong**.

## 4. Infrastructure changes can have large blast radius

Some Kubernetes operations are relatively harmless:

``` text
get_pods
get_nodes
get_events
get_pod_logs
```

They're read-only.

But operations such as:

``` text
delete deployment
scale deployment
update image
modify ConfigMap
modify Secret
delete PVC
change NetworkPolicy
```

can affect running applications, data, networking, or availability.

Therefore we shouldn't give the LLM unrestricted Kubernetes permissions.

## 5. Use least privilege

The agent should only have the permissions necessary for its job.

``` text
Agent ServiceAccount
        │
        ├── get pods
        ├── list pods
        ├── get logs
        ├── get events
        │
        └── limited approved write operations
```

Not:

``` text
cluster-admin ❌
```

Even if the LLM tries to perform an unauthorized operation, Kubernetes
RBAC should provide an independent enforcement layer.

``` text
LLM restrictions
      +
Tool restrictions
      +
Kubernetes RBAC
```

rather than trusting one layer.

## 6. Use HITL for sensitive operations

This is exactly why we implemented HITL in our Kubernetes agent.

Our current flow is:

``` text
User
 ↓
LangGraph Agent
 ↓
LLM
 ↓
Read tools
 ↓
Diagnose problem
 ↓
LLM proposes write operation
 ↓
approval node
 ↓
interrupt()
 ↓
PostgreSQL checkpoint
 ↓
Human
 ├── Reject → don't execute
 │
 └── Approve
       ↓
MCP write tool
       ↓
Kubernetes API
```

For example, our agent proposed:

``` text
update_deployment_image
deployment = nginx-app
image = nginx:1.27
```

Instead of immediately changing Kubernetes, LangGraph paused and asked
for human approval.

That is an important safety boundary.

## 7. Validate before execution

Human approval shouldn't be the only protection.

Before executing, the application can validate things such as:

``` text
Is this an allowed namespace?
Is this an allowed deployment?
Is this an approved image registry?
Is the image format valid?
Is this operation allowed?
Has cluster state changed since diagnosis?
```

A stronger production architecture is:

``` text
LLM proposes action
        ↓
Schema validation
        ↓
Policy validation
        ↓
Human approval
        ↓
Revalidate current state
        ↓
MCP tool
        ↓
Kubernetes RBAC
        ↓
Kubernetes API
```

## 8. Verify after the change

A common mistake would be:

``` text
MCP tool returned success
        ↓
Agent says:
"Application fixed."
```

That's not enough.

Instead:

``` text
Execute change
      ↓
Kubernetes accepts request
      ↓
Check Deployment
      ↓
Check rollout
      ↓
Check Pods
      ↓
Check readiness
      ↓
Report actual state
```

**Successful API execution does not necessarily mean successful
remediation.**

## Defense-in-depth architecture

The key concept for an interview is **defense in depth**:

``` text
                  LLM
                   ↓
            Tool allow-list
                   ↓
             Validation
                   ↓
                 HITL
                   ↓
              MCP Server
                   ↓
            Kubernetes RBAC
                   ↓
            Kubernetes API
                   ↓
          Post-change verification
```

We don't rely on the LLM itself to provide the security boundary.

## Interview Answer

> **I wouldn't trust an LLM directly with unrestricted Kubernetes
> changes because an LLM is probabilistic and can hallucinate,
> misunderstand user intent, choose the wrong tool, or generate
> incorrect tool arguments. Infrastructure changes can also have a
> significant blast radius. In my Kubernetes agent, I use defense in
> depth: read-only operations can execute automatically, sensitive write
> operations go through LangGraph HITL approval, tool inputs can be
> validated against policies, the MCP server exposes only permitted
> operations, and Kubernetes RBAC provides least-privilege enforcement.
> After executing a change, I query Kubernetes again to verify the
> actual resulting state rather than assuming that a successful API call
> means the problem was fixed.**

## Key Principle

> **The LLM can propose and reason, but deterministic controls should
> authorize, constrain, execute, and verify infrastructure changes.**

# What is grounding?

Grounding means providing an LLM with reliable external information so that its response is based on evidence rather than only on its pretrained knowledge. In my Kubernetes operations agent, I use MCP tools to ground the model with real-time Kubernetes state such as pods, logs and events, and I use RAG with Qdrant to ground troubleshooting recommendations in our Kubernetes runbooks. Grounding significantly reduces hallucination, although it doesn't completely eliminate it because the model can still misinterpret the supplied evidence.

So our agent has two particularly important grounding sources:
```
             LLM
            /   \
           /     \
          ↓       ↓
     MCP Tools    RAG
          ↓       ↓
   Live cluster   Runbooks
      state       knowledge
```

# What's the difference between an LLM and an agent?

An LLM is the reasoning and language-generation component, whereas an agent is a system built around an LLM that can reason, use tools, maintain state, and take actions to achieve a goal.

A simple way to remember it:
```
LLM = reasoning engine. Agent = LLM + tools + state/memory + control loop + actions.
```

# What is Arbitrary text ?

Arbitrary text means free-form, unstructured text that can contain almost anything, rather than text that must follow a predefined format.

```py
Arbitory Text:

The pod appears to be failing because the container image
cannot be pulled. You should verify the image name and tag.

Structured Text:

{
  "pod": "nginx-app",
  "status": "ImagePullBackOff",
  "cause": "Invalid image tag",
  "recommended_action": "Update the image"
}
```

```text
Arbitrary text
     ↓
Good for:
- explanations
- troubleshooting summaries
- normal chat responses

Structured output
     ↓
Better for:
- automation
- API processing
- tool arguments
- validation
- workflows
```

# Temperature vs top_p vs top_k?

All three are **generation/sampling parameters** that influence how an
LLM selects the **next token**, but they control the selection
differently.

The easiest way to remember them is:

> **Temperature = changes probability distribution.**\
> **top_k = keeps only the K most likely tokens.**\
> **top_p = keeps the smallest set of tokens covering P probability
> mass.**

Suppose the model has these simplified next-token probabilities:

  Token        Probability
  ---------- -------------
  restart              40%
  check                30%
  inspect              15%
  delete                8%
  recreate              4%
  ignore                3%

## 1. Temperature

**Temperature controls how sharp or flat the probability distribution is
before sampling.**

``` text
Low temperature
      ↓
High-probability tokens dominate more
      ↓
More predictable / consistent output

High temperature
      ↓
Distribution becomes flatter
      ↓
More variation / randomness
```

For example, with a lower temperature, `restart` and `check` become
relatively more dominant. With a higher temperature, lower-probability
alternatives get relatively more opportunity to be sampled.

For our Kubernetes operations agent, we'd generally favor **low
randomness** because we want consistent operational reasoning rather
than creativity.

Important:

> **Temperature = 0 does not mean zero hallucination.**

Grounding, validation and tool controls are still required.

## 2. top_k

**top_k limits sampling to the K highest-probability candidate tokens.**

Using our example, if:

``` text
top_k = 3
```

only these remain eligible:

``` text
restart  40%
check    30%
inspect  15%
----------------
delete    ❌
recreate  ❌
ignore    ❌
```

The probabilities of the remaining candidates are then handled by the
model's sampling process.

So:

> **top_k controls the candidate set by token count.**

If:

``` text
top_k = 10
```

up to the 10 most likely tokens are considered.

## 3. top_p

**top_p uses cumulative probability rather than a fixed number of
tokens.**

It is also called **nucleus sampling**.

Suppose:

``` text
top_p = 0.80
```

Starting from the most probable token:

``` text
restart    0.40    cumulative = 0.40
check      0.30    cumulative = 0.70
inspect    0.15    cumulative = 0.85
```

The smallest high-probability set reaching the threshold contains:

``` text
restart
check
inspect
```

The remaining low-probability tokens are excluded from that sampling
pool.

So:

> **top_p controls the candidate set by cumulative probability.**

This makes it different from top_k.

## top_k vs top_p

This is the key interview distinction.

``` text
top_k = fixed NUMBER of candidate tokens

top_p = dynamic NUMBER of candidate tokens
        based on cumulative probability
```

For example:

``` text
top_k = 5
```

means approximately:

> Consider the five highest-probability candidates.

Whereas:

``` text
top_p = 0.90
```

means:

> Consider the smallest set of high-probability candidates whose
> cumulative probability reaches a specified threshold.

That could be 3 tokens for one generation step and 50 tokens for
another.

## How they work together

Conceptually, you can think of generation as:

``` text
Prompt / Context
      ↓
LLM calculates logits
      ↓
Temperature adjusts distribution
      ↓
top_k / top_p restrict candidates
      ↓
Sample next token
      ↓
Append token to context
      ↓
Repeat
```

The exact order and supported parameters can vary by model/provider, so
don't assume every API implements all three identically.

## For our Kubernetes agent

We don't want the model being highly creative when diagnosing production
infrastructure.

``` text
Kubernetes Operations Agent

Temperature
    ↓
Generally low

top_p / top_k
    ↓
Usually conservative/default provider settings

More importantly:
    ↓
MCP grounding
RAG grounding
Tool validation
RBAC
HITL
Post-action verification
```

Sampling parameters can influence output consistency, but **they are not
security or factuality controls**.

You should never say:

> "I set temperature to zero, so the agent cannot hallucinate."

That would be incorrect.

## Interview Answer

> **Temperature, top_p, and top_k are sampling controls used during
> token generation. Temperature changes the shape of the probability
> distribution, where lower values generally make generation more
> deterministic and higher values increase variation. top_k restricts
> sampling to the K highest-probability tokens, while top_p, or nucleus
> sampling, restricts sampling to the smallest set of high-probability
> tokens whose cumulative probability reaches a specified threshold. For
> an operations agent, I generally prefer less randomness, but these
> parameters don't prevent hallucination; grounding through tools and
> RAG, validation, and safety controls are much more important.**

## Remember This

``` text
Temperature → How random?
top_k       → How many top candidates?
top_p       → How much probability mass?
```

# How Pprobability Calculates ??
```sh
Token          Probability
Paris             70%
Lyon              10%
Marseille           7%
London              5%
Berlin              3%
Rome                2%
Tokyo               1%
```

The probabilities don't initially exist as percentages. The neural network produces scores called logits, and those logits are converted into probabilities using softmax.

**Suppose you ask:**

```
"The capital of France is"
```

1. The Transformer processes the context
```
"The capital of France is"
          ↓
       Tokenizer
          ↓
       Token IDs
          ↓
      Embeddings
          ↓
Transformer layers
(Self-Attention + Feed Forward)
          ↓
Final hidden representation
```
Through training, the model has learned relationships between concepts and token patterns. So the final representation for this context strongly supports a token such as " Paris".

2. The model produces a score for every possible next token

The final hidden state is projected against the model's vocabulary.

Conceptually, suppose the vocabulary contains:

```
Paris
Lyon
Marseille
London
Berlin
Rome
Tokyo
...
```

The model might produce:

```
Token          Logit

Paris           8.0
Lyon            6.0
Marseille       5.5
London          4.5
Berlin          3.5
Rome            3.0
Tokyo           2.0
...
```

These numbers are called logits.
They are not probabilities.
```
You can't say:
Paris = 8%
```
A logit is simply a learned score indicating how strongly the model favors that token relative to the others.

3. Softmax converts logits → probabilities
```
Softmax essentially does:
\[
P(token_i)=\frac{e^{z_i}}{\sum_j e^{z_j}}
\]
```
where z is the token's logit.
Let's use a tiny example:
```
Paris     logit = 3
Lyon      logit = 2
London    logit = 1
```

Exponentiate them:
```
e³ = 20.09
e² =  7.39
e¹ =  2.72
             -----
Total       30.20
```

Now divide each by the total:
```
Paris:
20.09 / 30.20 = 0.665 = 66.5%

Lyon:
7.39 / 30.20 = 0.245 = 24.5%

London:
2.72 / 30.20 = 0.090 = 9.0%
```

Now:
```
Token       Probability

Paris          66.5%
Lyon           24.5%
London          9.0%
               -----
               100%
```

That's where the probability comes from.

### But where did the logits themselves come from?

That's the deeper answer.

After the Transformer processes your prompt, it has a final hidden vector representing the current context:
```
"The capital of France is"
             ↓
        Transformer
             ↓
     Final hidden state
             ↓
[h1, h2, h3, h4, ...]
```

That vector goes through the model's output projection / language-model head:
```
hidden state
     ↓
Linear projection
     ↓
one score per vocabulary token
     ↓
logits
```

If the model had, hypothetically, a vocabulary of 100,000 tokens, it would produce roughly:
```
100,000 logits

for that next-token position.
Something like:
Token ID     Token       Logit

18374        " Paris"      8.2
8273         " Lyon"       4.7
...
92871        " database"  -2.3
...
```
The training of the neural network is what causes " Paris" to receive a much stronger score in this context.
